# 시험용 적용 우선 규칙

시험 안내와 과제 지침이 우선한다. 외부로 과제·결과물 전송, git push, PR, 배포 및 Computer Use 자동 조작을 금지한다. 브라우저 화면은 응시자가 직접 검증한다. 아래 문서의 자동 조작·푸시·PR·배포에 관한 충돌 지침은 따르지 않는다. 스킬 설치에 실패해도 수동으로 본문을 읽어 작업을 계속한다. 현업 담당자와의 대화는 응시자가 직접 수행한다.

추천 구성은 **Matt Pocock의 요구사항·도메인·구현 스킬, Superpowers의 디버깅·완료 검증 스킬, pstack의 실제 동작 검증 스킬을 조합하는 방식**입니다. 시험에서는 “얼마나 많은 에이전트를 돌렸는가”보다 **업무 목적을 정확히 파악하고, 제한된 시간에 작동하는 결과물을 만들고, 그 결과를 설명할 수 있는가**가 중요하므로, 전체 프레임워크를 여러 개 설치하는 방식은 추천하지 않습니다.

첨부 인터뷰는 Cofa Probe가 **기술적 완성도·업무 주도 능력·결과물 이해**를 함께 평가하고, 현업 담당자 페르소나에게 질문해 숨은 요구사항을 파악하는 구조를 설명합니다. 다만 이는 인터뷰에서 설명한 평가 방식이며, 이번 SK하이닉스 예선의 구체적인 배점·시간·외부 스킬 반입 범위까지 확정해 주는 자료는 아닙니다. 아래 구성은 시험 환경에서 허용된 기능에 맞춰 적용하는 것을 전제로 합니다.

## 1. 최종 선발: 핵심 8개와 상황별 예비 3개

**8개를 모두 매번 실행하는 것이 아닙니다.** 시작 시 역할만 등록하고, 해당 상황이 발생할 때 필요한 본문을 읽도록 구성합니다. 링크는 확인한 실제 스킬 파일이며, 원본을 수정해야 하는 부분은 뒤에서 별도로 명시했습니다.

| 구분 | 선발 스킬 | 출처 | 맡길 역할 | 실행 시점 |
|---|---|---|---|---|
| 핵심 ① | [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) | Matt Pocock | 결과를 바꿀 중요한 질문을 도출해 요구사항 확정 | 과제 해석 직후 |
| 핵심 ② | [domain-modeling](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md) | Matt Pocock | 업무 용어·상태·계산 기준·예외 정의 | 도메인 해석과 설계 |
| 핵심 ③ | [implement](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md) | Matt Pocock | 합의한 범위를 작은 단위로 구현하고 검증·리뷰 연결 | 구현 단계 |
| 핵심 ④ | [tdd](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md) | Matt Pocock | 핵심 업무 규칙을 독립적인 기대값으로 테스트 | 계산·권한·상태 전이 등 |
| 핵심 ⑤ | [systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md) | Superpowers | 재현→원인 조사→가설 검증→최소 수정 | 실패·오류 발생 시 |
| 핵심 ⑥ | [create-verification-skill](https://github.com/backnotprop/pstack/blob/main/skills/create-verification-skill/SKILL.md) | pstack | 실제 앱의 실행·조작·관찰 절차를 만들고 직접 수행 | 첫 기능이 작동한 뒤 |
| 핵심 ⑦ | [code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md) | Matt Pocock | 요구사항 충족과 코드 품질을 별도로 검토 | 핵심 기능 완성 후 |
| 핵심 ⑧ | [verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md) | Superpowers | 최신 실행 증거 없이 완료를 선언하지 않도록 통제 | 완료 보고·제출 직전 |
| 예비 A | [benchmark-checklist](https://github.com/backnotprop/pstack/blob/main/skills/benchmark-checklist/SKILL.md) | pstack | 성능 측정의 오류·조건 차이·재현성 점검 | 속도·처리량 개선 과제 |
| 예비 B | [handoff](https://github.com/mattpocock/skills/blob/main/skills/productivity/handoff/SKILL.md) | Matt Pocock | 결정·현재 상태·실패·다음 행동 인계 | 세션 전환·컨텍스트 부족 |

여기서 검증 관련 스킬은 중복처럼 보이지만 역할이 다릅니다. **TDD는 개별 규칙의 정확성**, **pstack은 실제 사용 경로의 작동**, **code-review는 요구사항과 변경 내용의 일치**, **verification-before-completion은 완료 주장의 근거**를 담당합니다. 같은 테스트를 네 번 돌리는 구성으로 만들면 안 됩니다.

## 2. 시험에 맞추려면 반드시 조정할 부분

원본을 그대로 설치하면 시험에 불필요한 질문·문서·병렬 호출이 늘어날 수 있습니다. 아래는 **원본의 기본 동작이 아니라 제가 제안하는 시험용 수정 사항**입니다. 수정본에는 원본 출처와 변경 내역을 남기는 것이 좋습니다.

| 스킬 | 원본에서 확인한 동작 | 시험용 조정 |
|---|---|---|
| `grilling` | 설계 결정의 모든 가지를 해소할 때까지 질문하고 합의 확인 | 결과를 바꾸는 질문부터 최대 5개씩 제시. 답을 찾을 수 있는 파일은 먼저 읽고, 나머지는 중요도에 따라 질문 또는 명시적 가정 처리 |
| `domain-modeling` | 용어집·필요한 ADR 작성 | 용어는 핵심 5~15개부터. 결정 기록은 실제로 중요한 선택만 짧게 작성 |
| `implement` | TDD·리뷰를 호출한 뒤 현재 브랜치에 커밋 | 자동 커밋을 기본값에서 제거. 시험의 저장·제출 방식에 맞춰 처리 |
| `tdd` | 테스트할 공개 경계를 사용자에게 확인 | 착수 때 핵심 테스트 경계를 한 번 합의. 승인된 범위 안에서는 매 테스트마다 재승인하지 않음 |
| `systematic-debugging` | Superpowers의 별도 TDD 스킬을 참조 | TDD 호출을 Matt의 `tdd`로 연결. 세 차례 실패하면 무제한 수정 대신 범위 축소·대체 구현 여부를 판단 |
| `create-verification-skill` | 프로젝트별 검증 스킬과 기능 맵 생성 | 반복 검증이 필요한 앱에 적용. 짧은 분석·스크립트 과제는 같은 원칙을 실행 스크립트와 체크리스트로 축소 |
| `code-review` | 기준점과 `HEAD`의 diff, 두 병렬 리뷰 사용 | 미커밋 변경과 신규 파일도 포함. 서브에이전트가 없으면 요구사항·품질을 두 번의 별도 검토로 수행 |
| `verification-before-completion` | 완료 주장 전에 새 검증 실행 요구 | 최종 변경본을 검증하고 이후 관련 변경이 없으면 증거 재사용. 영향받는 부분이 바뀌면 재검증 |
| `handoff` | OS 임시 디렉터리에 인계 문서 저장 | 시험에서 세션 간 보존되는 작업 디렉터리에 저장하고 실제 접근 가능 여부 확인 |

**특히 `code-review`의 diff 범위는 주의해야 합니다.** 원본은 `HEAD`를 기준으로 커밋된 변경을 비교하므로, 시험에서 커밋 없이 작업하면 실제 작성한 코드가 리뷰 대상에서 빠질 수 있습니다. 미추적 파일까지 포함해 확인하도록 바꿔야 합니다.

또한 스킬 파일 하나만 가져오면 충분하지 않을 수 있습니다. `tdd`의 `tests.md`, `mocking.md`, 도메인 모델링의 문서 양식처럼 **상대 경로로 참조되는 파일도 함께 확보**해야 합니다. 없는 `Skill` 도구를 호출하도록 방치하지 말고, 시험 에이전트가 지원하는 스킬 호출이나 파일 읽기로 연결해야 합니다.

## 3. 인터뷰의 팁을 실제 작업으로 바꾸는 방법

**첫 번째는 질문의 상대를 구분하는 것입니다.** `grilling`은 기본적으로 사용자에게 질문하지만, Cofa Probe에서 현업 페르소나가 제공된다면 업무 사실은 그 페르소나에게 확인해야 합니다. “수율의 분모가 무엇인가”를 수험생에게 계속 묻거나 에이전트가 상식으로 채우게 하면 안 됩니다. 에이전트는 질문 후보를 정리하고, 제공된 인터페이스를 통해 답을 확보한 뒤 사용자가 범위와 우선순위를 결정하도록 해야 합니다.

질문은 “무엇을 만들까요?”보다 **답에 따라 구현이 달라지는 질문**이어야 합니다. 예를 들어 설비 이상 대응 도구라면 다음과 같은 순서가 유용합니다.

- 이 결과를 누가 보고 어떤 행동을 결정하는가?
- 반드시 놓치면 안 되는 이상과, 허용 가능한 오탐은 무엇인가?
- 데이터 한 행은 어떤 단위이며 시간 기준은 무엇인가?
- 정상·이상·조치 완료의 정의와 근거는 어디에 있는가?
- 이번 제출에서 실제로 동작해야 하는 범위와 제외해도 되는 범위는 무엇인가?

**두 번째는 사람이 판단할 지점을 작게 유지하는 것입니다.** 착수 시 목표와 성공 조건, 구현 중 중요한 범위 변경, 제출 전 한계와 검증 결과 정도를 직접 판단하면 됩니다. 모든 세부 구현에 승인 절차를 넣으면 시간이 소모되고, 반대로 전체 결정을 에이전트에 넘기면 인터뷰가 강조한 주도성과 이해가 약해집니다.

**세 번째는 설명을 작업 도중 확보하는 것입니다.** 핵심 기능을 완성할 때마다 “입력→처리→출력, 선택 이유, 검증 방법, 남은 한계”를 짧게 설명받고 실제 결과와 대조하세요. 제출 직전에 긴 설명문을 생성하는 것보다, 자신이 이해하지 못하는 결정을 일찍 발견하는 데 유리합니다.

## 4. 회사 운영·반도체 문제에는 별도의 데이터 규칙이 필요하다

선발한 스킬만으로 반도체 전문지식이나 분석 정확성이 보장되지는 않습니다. **문제에서 제공한 정의를 우선하고, 수치의 의미를 검증하는 규칙**을 공통 지침에 넣어야 합니다. 다음은 출제 예측이 아니라 해당 유형이 나왔을 때 확인할 항목입니다.

| 문제 유형 | 구현 전에 확정할 내용 | 반드시 해볼 검증 |
|---|---|---|
| 수율·불량 분석 | 분자·분모, 집계 단위, 재검사·재작업 포함 여부 | 비율의 단순평균과 전체 분자÷전체 분모 비교, 작은 표본 수계산 |
| 설비 운영·가동률 | 예정 시간·정지 시간·가동 시간 정의, 중첩 이벤트 처리 | 시간 구간 합계, 중복 집계, 날짜 경계 확인 |
| 생산·인력 배치 | 목적함수, 필수 제약, 우선순위, 해가 없을 때의 처리 | 자원 중복 배정·용량 초과 검사, 단순 기준안과 비교 |
| 비용·재고·구매 | 통화·단위·기준 기간, 비용 항목, 결측치 의미 | 단위 환산, 합계 대조, 극단값·0·음수 처리 |
| 예측·이상 탐지 | 예측 시점, 사용 가능한 정보, 정답 정의 | 시간 누수·동일 LOT 중복 분할 여부, 단순 기준 모델 비교 |

예를 들어 “수율이 3% 개선됐다”는 결과에는 상대 변화율인지 3%p 상승인지, 어떤 표본과 기간을 비교했는지가 필요합니다. `benchmark-checklist`는 소프트웨어 성능 검증용이므로 이런 도메인 검증을 전부 대신하지 못합니다.

## 5. 이번 구성에서 제외할 것

이전 추천의 GSD·BMAD·OMC·ECC·gstack이 나쁘다는 의미는 아닙니다. **시험용 기본 구성에서 역할이 겹치거나 준비 비용이 큰 부분을 빼는 것**입니다.

| 제외 대상 | 이번에 제외하는 이유 |
|---|---|
| 전체 GSD·BMAD 프로세스 | 초기 설정·단계별 산출물·프로젝트 관리가 짧은 시험에 과할 수 있음 |
| OMC·OMX 전체 오케스트레이션 | 제공 환경의 병렬 실행·세션 제어 지원이 불확실함 |
| ECC 전체 설치 | 스택을 알기 전에 방대한 규칙을 넣을 필요가 없음 |
| gstack의 제품·출시 전체 흐름 | 이번 구성의 요구사항·리뷰·검증과 중복. 별도 브라우저 도구 설치도 부담 |
| Superpowers 전체 진입 흐름 | 선택한 Matt 스킬과 질문·계획·TDD·리뷰 역할이 겹침 |
| pstack `poteto-mode` 전체 | 다수 플레이북·모델 라우팅·스킬 의존성이 기본 구성보다 큼 |
| pstack `architect` 기본 방식 | 여러 설계 후보를 병렬 생성하는 절차는 복잡한 설계 과제가 아니면 비용이 큼 |
| Matt `grill-with-docs` | 이미 선발한 `grilling`과 `domain-modeling`을 호출하는 래퍼이므로 생략 |

시험 과제가 큰 기존 시스템 변경이거나 여러 시간의 자율 개발을 요구한다면 이 선택은 달라질 수 있습니다. 하지만 처음부터 모든 가능성을 위한 프레임워크를 얹기보다는, 실제 과제에 필요한 예비 스킬만 추가하는 편이 낫습니다.

## 6. 시험 에이전트에 전달할 적용 지침

아래 지침과 위 선발표의 링크를 함께 전달하면 됩니다. **원본을 무조건 실행하라는 지시가 아니라, 시험 조건에 맞게 선별·적용하라는 지시**입니다. 가능하다면 시험 전에 같은 구성으로 모의 과제를 한 번 실행해 파일 접근과 스킬 호출부터 확인하세요.

```text
이 과제에서는 아래 선발 스킬을 시험용으로 조정하여 사용한다.
```

**1. `grilling` — 틀린 문제를 열심히 푸는 일을 방지한다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)은 질문을 통해 계획과 설계의 빈틈을 해소합니다. 결정 하나가 다음 결정을 어떻게 바꾸는지 트리처럼 생각하고, 현재 답할 수 있는 질문들을 묶어서 묻습니다. 앞선 답이 있어야 판단할 수 있는 질문은 다음 라운드로 넘깁니다.

예를 들어 “불량률을 낮추는 대시보드를 만들어라”라는 요청에는 구현에 앞서 풀어야 할 문제가 있습니다. 누가 사용하는지, 어떤 행동을 돕는지, 불량률을 어떤 기준으로 계산하는지, 조기 경보가 필요한지 사후 분석이 필요한지에 따라 결과물이 달라집니다. 이 단계에서 화면부터 만들면 중요한 차이를 뒤늦게 발견하게 됩니다.

실전에서는 **답에 따라 구현 범위나 정답이 바뀌는 질문**을 우선합니다. 색상이나 레이아웃보다 “이상 징후를 발견한 담당자가 어떤 조치를 해야 하는가”, “LOT 단위 분석인가 장비 단위 분석인가”, “필수 제출 기능은 무엇인가”를 먼저 확인해야 합니다.

사용 지시는 다음처럼 구체적으로 작성하면 됩니다.

> `grilling`을 사용해 과제의 핵심 불확실성을 찾아라. 먼저 README와 제공 데이터를 조사하고, 파일에서 확인되지 않으면서 구현 결과를 바꾸는 질문을 최대 5개 제시해라. 각 질문에는 확인 대상, 답에 따라 달라지는 구현, 권장안을 붙여라. 업무 사실은 현업 페르소나에게 확인할 질문으로, 범위와 우선순위는 내가 결정할 질문으로 구분해라.

원본은 모든 결정의 가지를 해소하고 사용자와 이해가 일치할 때까지 질문하는 방식입니다. **시험용으로는 필수 기능을 구현할 수 있을 만큼의 중요한 불확실성이 해소되면 진행**하도록 조정하는 것이 좋습니다. 사소한 사항은 가정으로 기록하고, 정답이나 핵심 동작을 바꾸는 사항은 추측하지 않습니다.

이 스킬이 잘 끝났다는 기준은 질문 개수가 아닙니다. **대상 사용자, 해결할 문제, 필수 결과물, 성공 조건, 제외 범위**를 본인이 설명할 수 있으면 됩니다.

**2. `domain-modeling` — 업무 언어를 코드와 계산의 기준으로 만든다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md)은 모호한 용어를 구체화하고, 업무 관계와 예외를 검토하며, 결정된 의미를 용어집에 반영합니다. 기존 용어집과 발언이 충돌하거나, 설명한 업무 규칙과 코드가 다르면 그 차이를 드러냅니다.

`grilling`이 “무엇을 확인해야 하는가”를 해결한다면, 이 스킬은 **확인한 답을 일관된 업무 모델로 정착시키는 역할**을 합니다. 특히 반도체·운영·재무 과제에서는 변수 이름보다 변수의 의미가 먼저입니다.

예를 들어 제공 데이터에 `yield`가 있더라도 다음은 자동으로 확정되지 않습니다.

| 확인 항목 | 구현에 미치는 영향 |
|---|---|
| 최초 검사 기준인지 최종 검사 기준인지 | 재검사 데이터를 포함하는 방식 |
| 분모가 투입 수인지 검사 완료 수인지 | 계산식과 결측 처리 |
| 행별 비율을 평균하는지 전체 수량으로 계산하는지 | 집계 결과 |
| 수량이 없는 LOT를 어떻게 처리하는지 | 오류·제외·미산출 표시 |

실전 지시는 다음처럼 할 수 있습니다.

> `domain-modeling`을 적용해 과제의 핵심 용어와 계산 규칙을 정리해라. 제공 문서·페르소나 답변·데이터에서 확인한 정의를 우선하고, 일반 지식으로 채운 부분은 가정으로 표시해라. 특히 데이터 한 행의 단위, 식별자, 시간 기준, 분자·분모, 상태 전이, 결측·중복·재검사 처리 기준을 확인해라.

이때 용어집에는 업무 의미를 적고, 구현 계획이나 진행 상황을 섞지 않는 것이 좋습니다. “LOT는 무엇인가”와 “LOT 목록 API를 어떤 파일에 구현하는가”는 다른 종류의 정보입니다.

**시험용 조정**으로는 핵심 용어부터 소수로 시작하고, 중요한 기술 선택만 결정 기록으로 남깁니다. 원본도 ADR을 무조건 많이 만들도록 요구하지 않으며, 되돌리기 어렵고 실제 대안 간 선택이 있었던 중요한 결정에 한정합니다.

완료 기준은 **같은 용어가 화면·계산·테스트·설명에서 같은 의미로 쓰이는지**입니다. 문서를 길게 만드는 것이 목적은 아닙니다.

**3. `implement` — 합의한 내용을 작은 작동 단위로 바꾼다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md)은 명세나 티켓을 구현하고, 합의한 경계에서 TDD를 사용하며, 타입 검사와 테스트를 수행한 뒤 코드 리뷰로 마무리합니다. 원본에는 현재 브랜치에 커밋하는 동작도 포함되어 있습니다.

이 스킬은 요구사항을 결정하는 역할보다 **정해진 요구사항을 실행하는 역할**에 가깝습니다. 따라서 처음부터 “이 스킬로 전체를 알아서 만들어”라고 지시하기보다 범위와 완료 조건을 먼저 줘야 합니다.

대시보드라면 “백엔드 전체→프론트엔드 전체→마지막 연결”보다 **데이터 한 개를 읽어 핵심 지표 하나를 계산하고 화면에 표시하는 경로**부터 완성하는 것이 좋습니다. 이 첫 경로가 환경·데이터·계산·화면 연결의 문제를 일찍 드러냅니다.

> `implement`로 필수 기능 중 ‘CSV 업로드→LOT별 수율 계산→결과 표시’ 경로부터 구현해라. 기존 기술 스택과 실행 명령을 유지하고, 이 경로를 검증하기 전에는 추가 차트나 부가 기능으로 확장하지 마라. 각 단위가 끝나면 변경 내용과 실행 결과를 보고해라.

작업 단위는 “파일 세 개 수정”보다 “사용자가 관찰할 수 있는 행동 하나”로 잡는 것이 유용합니다. 파일은 여러 개 바뀌어도 되지만 완료 여부를 확인할 수 있어야 합니다.

**시험용 조정**으로는 자동 커밋을 제거하고 제출 지침을 따르게 합니다. 또 명세에 없는 인증 시스템, 범용 플러그인 구조, 복잡한 배포 구성을 추가하지 않도록 범위를 제한합니다.

완료 기준은 코드 작성량이 아니라 **해당 기능의 입력·처리·출력이 실제로 연결되고, 합의한 검사가 통과했는지**입니다.

**4. `tdd` — 중요한 업무 규칙이 틀렸을 때 실패하는 검사를 만든다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)은 공개된 인터페이스에서 행동을 검증하고, 한 번에 작은 수직 단위로 실패 테스트와 구현을 반복하도록 합니다. 내부 메서드 호출 순서나 세부 구현에 과도하게 묶인 테스트, 구현과 같은 계산을 복사한 테스트를 피합니다.

해커톤에서는 다음과 같이 **오답의 비용이 큰 부분**에 우선 적용하세요.

- 수율·비용·가동률처럼 결과의 신뢰성을 좌우하는 계산.
- 경보 임계값과 경계값 비교.
- 권한이나 승인 조건.
- 중복 제거와 데이터 변환.
- 작업 배정의 필수 제약과 상태 전이.

예를 들어 불량률 계산을 테스트한다면 작은 입력에서 사람이 계산한 기대값을 사용합니다. “전체 100개 중 불량 4개면 4%”처럼 독립적으로 확인 가능한 값이 필요합니다. 테스트 안에서 구현과 같은 함수를 호출하거나 동일한 복잡한 계산을 다시 수행하면 함께 틀릴 수 있습니다.

> `tdd`를 적용하되 공개 경계는 ‘집계 함수의 입력과 반환값’으로 하자. 정상 사례, 분모 0, 결측 수량, 크기가 다른 LOT의 가중 집계를 우선 검증해라. 기대값은 작은 예제의 수계산으로 확정하고, 실패를 확인한 뒤 최소 구현을 추가해라.

원본은 테스트 경계를 사용자에게 먼저 확인하도록 합니다. **시험용으로는 착수 때 핵심 경계를 한 번 합의하고 그 범위에서 계속 진행**하도록 조정하세요. 모든 테스트마다 승인을 받으면 흐름이 끊깁니다.

또한 화면 여백이나 단순 문구까지 동일한 방식으로 테스트할 필요는 없습니다. 제한된 시간에는 핵심 계산과 동작의 오류를 잡는 검사를 먼저 확보하는 것이 좋습니다.

완료 기준은 “테스트가 초록색”만이 아닙니다. **잘못된 구현을 넣었을 때 실제로 실패하는 테스트인지**도 중요합니다.

**5. `systematic-debugging` — 추측성 수정이 누적되는 것을 막는다**

[원본 스킬](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)은 원인 조사, 정상 사례와 비교, 단일 가설 검증, 최소 수정의 순서로 진행합니다. 에러가 발생했다고 곧바로 여러 파일을 바꾸지 않도록 하는 것이 핵심입니다.

가령 화면에서 CSV 업로드가 실패하면 원인은 파일 파싱, 요청 형식, API 주소, 서버 실행, 데이터 검증 중 어디에나 있을 수 있습니다. “CORS 문제일 것 같다”는 추측으로 설정부터 바꾸면 원래 문제가 가려질 수 있습니다.

> `systematic-debugging`으로 업로드 실패를 조사해라. 동일 파일로 재현하고 브라우저 요청·응답과 서버 로그를 확인해 실패 경계를 찾아라. 현재 가설, 근거, 가설을 구분할 최소 실험을 제시한 뒤 한 번에 한 원인만 수정해라.

좋은 디버깅 보고는 “여러 설정을 고쳤다”보다 **“요청은 서버에 도달했지만 필드명이 달라 검증 단계에서 거절됐다”**처럼 실패 위치가 명확합니다. 수정 후에는 원래 실패 입력을 다시 실행하고 관련 정상 사례도 확인해야 합니다.

원본은 세 차례 이상 수정 실패가 이어지면 구조적 문제를 의심하고 사용자와 논의하도록 합니다. 시험에서는 이 지점을 **대체 라이브러리, 단순한 구현, 기능 범위 축소를 결정하는 시점**으로 활용할 수 있습니다.

주의할 점은 “원인은 반드시 코드에 있다”고 고집하지 않는 것입니다. 제공 환경의 권한·네트워크·브라우저 제한이 원인이라면 조사한 증거와 미검증 범위를 남겨야 합니다.

**6. `create-verification-skill` — 실제 앱을 반복해서 검증할 방법을 만든다**

[원본 스킬](https://github.com/backnotprop/pstack/blob/main/skills/create-verification-skill/SKILL.md)은 프로젝트에 맞는 검증 스킬을 생성합니다. 실행 방법, 정상 상태 확인, 사용자 행동 재현, 증거 수집, 정리 절차를 코드베이스에서 조사하고, 생성한 절차를 실제로 한 번 실행하도록 요구합니다.

예를 들어 대시보드에서는 단위 테스트가 통과해도 업로드 버튼이 API와 연결되지 않았거나, 필터를 바꿔도 결과가 갱신되지 않을 수 있습니다. 이 스킬은 **사용자가 실제로 거치는 경로**를 검증하도록 만듭니다.

> `create-verification-skill`로 이 앱의 검증 절차를 만들어라. 기존 실행 환경과 테스트 도구를 우선 사용하고, 샘플 CSV 업로드→지표 표시→필터 변경→빈 결과 확인 경로를 재현해라. 화면 결과와 필요한 API·저장 상태를 관찰하고, 생성한 절차를 직접 실행해 증거를 남겨라.

원본이 생성하도록 하는 주요 내용은 다음과 같습니다.

| 구성 | 확인하는 것 |
|---|---|
| Launch | 앱을 어떻게 실행하고 사용 가능한 상태인지 판별하는가 |
| Doctor | 올바른 인스턴스·버전·인증 상태인지 확인하는가 |
| Drive | 실제 기능을 어떤 명령·선택자로 조작하는가 |
| Evidence | 어떤 결과가 기능의 성공을 증명하는가 |
| Cleanup | 생성한 프로세스와 임시 상태를 어떻게 정리하는가 |

이 스킬은 **검증 절차를 만드는 도구**입니다. 기능 변경 때마다 생성기를 다시 실행할 필요는 없습니다. 한 번 만든 프로젝트 검증 스킬이나 스크립트를 반복 사용하면 됩니다.

**시험용 조정**으로, 일회성 데이터 분석 과제는 별도 기능 맵과 스킬 체계를 만드는 대신 재현 가능한 분석 명령과 결과 검사를 남겨도 됩니다. 검증 자동화를 구축하는 데 본 과제보다 많은 시간을 쓰지 않도록 해야 합니다.

**7. `code-review` — ‘잘 작성했는가’와 ‘요청대로 만들었는가’를 구분한다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)은 변경 사항을 두 축으로 검토합니다. Standards는 저장소의 코드 규칙과 품질을, Spec은 원래 요구사항의 충족 여부를 확인합니다. 원본은 두 관점을 병렬 서브에이전트에 맡겨 서로의 판단에 영향을 덜 받도록 합니다.

이 구분은 시험에서 중요합니다. 구조가 깔끔하지만 가중평균을 잘못 계산한 코드, 기능은 맞지만 필수 제출 형식을 지키지 않은 결과물이 나올 수 있기 때문입니다.

> `code-review`를 수행해라. 요구사항 관점에서는 누락·오해·불필요한 확장을, 품질 관점에서는 실제 오류 가능성과 유지보수 문제를 확인해라. 미커밋 변경과 신규 파일까지 포함하고, 제출을 막는 결함과 선택적 개선을 구분해라.

시험에서는 발견한 사항을 모두 수정할 필요는 없습니다.

| 우선순위 | 예시 | 대응 |
|---|---|---|
| 즉시 수정 | 계산 오류, 앱 실행 실패, 필수 기능 누락 | 수정 후 재검증 |
| 시간 확인 후 수정 | 중요한 입력에서 오류, 잘못된 상태 표시 | 영향과 수정 시간을 비교 |
| 보류 가능 | 이름 취향, 작은 중복, 부가적인 추상화 제안 | 제출 전 확장하지 않음 |

원본은 Git 기준점과 `HEAD`의 변경을 비교합니다. **시험용으로 미커밋 변경·미추적 신규 파일까지 포함하도록 바꾸지 않으면 실제 구현이 리뷰에서 빠질 수 있습니다.**

또한 서브에이전트를 사용해도 같은 모델의 검토가 완전히 독립적인 정답 검증은 아닙니다. 실행 검사와 독립적인 기대값이 계속 필요합니다.

**8. `verification-before-completion` — 완료 주장을 증거와 연결한다**

[원본 스킬](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)은 완료를 주장하기 전에 그 주장을 증명하는 명령을 실행하고, 전체 출력과 종료 상태를 확인하도록 합니다.

빌드 성공은 기능 정상 작동을 증명하지 않습니다. 단위 테스트 통과는 화면 연결을 증명하지 않고, 서버가 켜졌다는 사실은 데이터 처리가 올바르다는 뜻이 아닙니다. **주장마다 그에 맞는 증거**가 있어야 합니다.

> `verification-before-completion`을 적용해 제출 상태를 점검해라. 필수 요구사항별로 검증 방법과 실제 결과를 대조하고, 완료·실패·미검증을 구분해라. 마지막 관련 변경 이후 실행한 증거만 사용하고, 확인하지 못한 부분을 완료로 표현하지 마라.

최종 보고는 다음 정도로 간결하면 됩니다.

| 요구사항 | 검증 | 결과 |
|---|---|---|
| LOT별 지표 집계 | 수계산 예제와 자동 테스트 비교 | 통과 |
| CSV 업로드 | 실제 화면에서 샘플 업로드 | 통과 |
| 잘못된 파일 안내 | 필수 열 누락 파일 업로드 | 통과 |
| 외부 시스템 연동 | 제공 환경에서 접근 불가 | 미검증 |

**시험용 조정**으로는 최종 변경본을 검증한 뒤 관련 코드가 바뀌지 않았다면 같은 증거를 재사용하도록 합니다. 단순 보고 문장을 쓸 때마다 전체 테스트를 반복할 필요는 없습니다. 반대로 집계 코드를 고친 뒤 이전 집계 테스트 결과를 그대로 제출하면 안 됩니다.

**9. 예비 `how` — 기존 코드의 변경 지점을 정확히 찾는다**

[pstack의 원본 스킬](https://github.com/backnotprop/pstack/blob/main/skills/how/SKILL.md)은 시스템의 개념, 실행 흐름, 파일 위치, 주의점을 설명하도록 합니다. 기존 프로젝트를 수정하는 과제에서 유용하며, 완전한 신규 프로젝트라면 우선순위가 낮습니다.

좋은 질문은 “저장소 전체를 분석해”보다 **수정하려는 기능의 흐름을 추적해 달라는 요청**입니다.

> `how`로 CSV 업로드가 화면에서 시작해 집계 결과로 반환되는 경로를 추적해라. 진입점, 검증 단계, 계산 위치, 저장 여부, 기존 테스트를 설명하고, 이번 요구사항을 반영할 최소 수정 지점을 찾아라.

결과를 받은 뒤에는 핵심 파일과 설명을 직접 대조하세요. 에이전트가 파일명만 보고 역할을 추측하지 않았는지, 실제 호출 흐름과 일치하는지 확인하는 과정입니다.

원본은 여러 모델과 탐색·설명 에이전트를 활용할 수 있습니다. **시험용으로는 작은 기능은 단일 에이전트가 조사하고, 사용 가능한 모델을 상속**하도록 조정하면 됩니다. 전체 코드베이스 탐색은 필요한 범위를 확인한 뒤 확대하세요.

**10. 예비 `benchmark-checklist` — 빠르다는 숫자가 무엇을 의미하는지 확인한다**

[원본 스킬](https://github.com/backnotprop/pstack/blob/main/skills/benchmark-checklist/SKILL.md)은 병목, 설정 조건, 오류, 반복 측정, 사용자 관점의 효과, 실제 작업 수행 여부를 확인합니다. 성능 개선 과제나 “처리 시간이 줄었다”는 주장을 할 때 사용합니다.

예를 들어 수정 후 응답이 빨라졌지만 실제로는 입력 일부를 누락하거나 오류를 빨리 반환했다면 개선이 아닙니다. 캐시가 채워진 결과와 최초 실행을 비교해도 해석이 달라집니다.

> `benchmark-checklist`로 개선 주장을 검증해라. 같은 데이터와 실행 조건에서 기존·수정 버전을 비교하고, 출력의 동일성과 오류 수를 확인해라. 반복 실행의 중앙값과 범위를 보고하고, 측정 대상과 전체 처리 시간을 구분해라.

원본은 본격 비교에서 각 버전을 최소 다섯 번 번갈아 실행하는 방식을 제시합니다. 시험 시간상 충분히 수행하지 못했다면 **단일 실행 관측인지, 반복 비교 결과인지**를 구분해서 보고하면 됩니다.

이 스킬은 소프트웨어 성능 측정용입니다. 제조 수율 개선의 인과관계나 예측 모델의 통계적 타당성을 자동으로 검증해 주지는 않습니다. 해당 분석에는 문제에 맞는 데이터 분할·표본·비교 기준이 별도로 필요합니다.

**11. 예비 `handoff` — 다음 세션이 같은 실수를 반복하지 않게 한다**

[원본 스킬](https://github.com/mattpocock/skills/blob/main/skills/productivity/handoff/SKILL.md)은 대화를 다음 에이전트가 이어갈 수 있는 문서로 압축합니다. 이미 명세·코드·결정 기록에 있는 내용은 경로로 참조하고, 다음 세션에서 사용할 스킬을 안내합니다.

컨텍스트가 거의 찬 뒤 작성하면 핵심 정보가 누락될 수 있으므로, 세션 전환이 예상되거나 설명이 길어져 같은 질문이 반복되기 시작하면 사용하세요.

> `handoff`를 작성해라. 현재 목표와 완료 조건, 중요한 결정과 이유, 수정 파일, 마지막 검증, 아직 실패하는 재현 절차, 시도했지만 실패한 방법, 다음 행동을 우선순위대로 남겨라. 기존 문서는 경로로 참조하고, 다음 세션에서 접근 가능한 위치에 저장해라.

인계에서 가장 가치 있는 정보는 최종 상태와 실패 이력입니다. “업로드 작업 중”보다 “정상 CSV는 통과하며, 빈 날짜가 있는 행에서 변환 오류가 발생한다. 날짜 열을 모두 문자열로 바꾸는 방식은 정렬을 깨뜨려 되돌렸다”가 다음 작업 시간을 줄여 줍니다.

원본은 OS 임시 디렉터리에 저장하도록 합니다. **시험용으로는 세션 간 보존되는 경로로 조정하고 실제 파일이 존재하는지 확인**해야 합니다. 새 세션에서는 인계문만 믿지 말고 코드 상태와 핵심 검증 결과를 다시 확인해야 합니다.

마지막으로, 이 구성을 실제 시험에서 운용할 때는 **세 번의 사람 판단 지점**을 두는 것이 적절합니다. 시작할 때 목표·필수 범위·성공 조건을 확정하고, 첫 번째 기능이 실제로 작동했을 때 방향을 확인하며, 제출 전에 검증 결과와 한계를 확인하세요. 나머지 구현과 반복 검사는 합의한 범위 안에서 에이전트가 계속 진행하도록 하면 됩니다.

가령 설비 이상 분석 대시보드 과제라면 `grilling`으로 담당자의 의사결정을 확인하고, `domain-modeling`으로 이상·시간·집계 단위를 정한 다음, 기존 코드가 있으면 `how`로 변경 지점을 찾습니다. 이후 `implement`와 `tdd`로 첫 경로를 완성하고, 오류가 날 때만 `systematic-debugging`을 사용합니다. 실제 사용자 경로를 검증하고 `code-review`로 누락을 점검한 뒤, `verification-before-completion`으로 제출 상태를 확정하면 됩니다. **성능 측정과 세션 인계가 필요하지 않다면 예비 스킬은 끝까지 호출하지 않아도 됩니다.**
