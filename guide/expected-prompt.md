개선안 구현 진행할거야.  세개의 각각의 다른 개선 알고리즘을 선택 한 후 설계해, 해당 개선안을 고른 이유를 문서화해. 

문제에서 최적해를 요구하지 않는다면 설명과 검증이 가능한 단순한 방법부터 검토해. 최적이라고 증명하지 못한 결과를 최적해라고 표현하지 마 (“최적화”와 “최적해”는 다르다).

구현된 세개의 알고리즘, 결과물을 레이팅할 기준을 세울거야. 단순히 한 두개의 수치가 개선된게 높은 등급이 아니고,  과제의 요구사항을 바탕으로 필수조건이나 우선조건등을 판별해서 가중치를 다 다르게 둬야돼. 이 가중치를 어떻게 정할지도 구상 후 리뷰해서 확정 작업 해.

선별 기준을 바탕으로 만든 개선안 세개를 리뷰하고 순위를 매겨줘. 그리고 왜 이런 선택을 했는지도 문서화해야돼. 개선된 판정 로직과 결과	기준안과 달라진 이유도 작성해.

결과 독립 검증	테스트 결과, 비교표, 오류 등이 실제 근거와 결과가 일치하는지 유의해야돼. 과도하게 오버피팅되어 있지 않도록 유의해야돼.

---

기준안과 개선안을 작은 테스트 구현해서 평가할거야. 즉 전체 데이터에 적용하기 전에 작은 테스트를 만들어서 동일한 데이터 범위와 조건에서 실행해 줘. 확정된 지표만 계산하고 결과를 docs/work에 숫자를 붙이고 comparison 파일 저장해.

각 지표에 계산식, 실제 값 등을 표시하고 처리 건수와 이유도 적어. 

결과가 달라진 대표 사례를 3개까지 골라 기준안 결과, 개선안 결과, 차이가 발생한 규칙과 근거를 설명해 줘. 정답 데이터가 없으면 정확도나 오탐률을 계산하지 마. 측정하지 않은 실제 업무 시간 절감 효과도 주장하지 마.

---

기존 구현을 다시 설명하지 말고 검증자 관점에서 점검해 줘.

1. 규정 문서의 각 핵심 규칙과 실제 구현을 대조한다.
2. 경계값, 누락값, 중복 후보, 연결 실패를 검증한다.
3. 기준안과 개선안이 같은 데이터 범위를 사용하는지 확인한다.
4. 화면에 표시되는 수치가 계산 결과와 일치하는지 확인한다.
5. 검증하지 못한 항목은 통과로 표시하지 않는다.

가능하면 기존 구현 함수와 별도로 기대 결과를 계산하거나 작은 고정 데이터의 기대값을 직접 명시해 비교해.

실행 명령, 실제 결과, 실패 항목, 근거 파일을 docs/work에 independent-verification 파일 만들어서 기록해.

검증 결과가 틀렸다면 방금 확인된 검증 실패를 수정해 줘.

수정 전에:
- 기대 결과와 실제 결과
- 원인으로 확인된 코드 또는 데이터
- 영향을 받은 결과와 화면

을 정리하고, 수정 후 같은 테스트를 다시 실행해. 새로 확인된 미해결 문제는 기존 부채 기록 방식에 맞춰 남겨. 실패를 재현하지 못했으면 추측을 원인으로 확정하지 마.

# 웹사이트 제작

다른 세션에서 기준안을 바탕으로 개선 알고리즘을 작성하고 있어. 이 세션에서는 독립적으로 웹 서비스 구현을 진행할거야. 실제 판정 결과와 사용자 권한이 연결되어 있는지가 중요하고, 직원·관리자가 사용할 화면 및 API 등을 원활하게 구현할 수 있도록 지금까지 문서화한걸 바탕으로 prd를 작성해. 화면과 백엔드가 서로 다른 결과 구조를 가정하지 않도록 먼저 계약을 정해야 돼. 주요 사용자 흐름도 문서화해서 어떻게 사용하는지도 작성해줘.

해당 prd를 바탕으로 planning을 통해 각각의 서브에이전트마다 어떻게 병렬작업할건지 계획해줘.

작업 진행하고 작업 시에 생기는 기술 부채들은 누락하지 말고 기록해줘 

---

실제 사용자 흐름을 처음부터 끝까지 검증할거야. 과제의 핵심 사용자 흐름을 실제 실행 환경에서 검증해.

1. 제공 데이터를 읽는다.
2. 규칙 판정 결과를 생성한다.
3. API가 해당 결과를 반환한다.
4. 직원 화면에 본인의 결과가 표시된다.
5. 관리자 화면에 전체 현황과 판정 사유가 표시된다.
6. 직원이 다른 직원의 데이터에 접근할 수 없는지 확인한다.

각 단계의 실행 방법과 실제 결과를 docs/work/에 end-to-end-check 파일 만들어서 기록해. 실행하지 못한 단계는 성공으로 쓰지 말고 이유를 적어 줘.
