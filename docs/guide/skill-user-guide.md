# 스킬 실전 사용 가이드

이 문서는 시험 중 응시자가 상황에 맞는 스킬을 고르고 Codex에 요청하기 위한 참고 자료다. 시험 공지와 과제 README가 우선한다. 본 과제에서만 허용된 Codex를 사용하며, 후속 서술형에서는 안내된 AI 사용 금지를 따른다.

## 시작: 저장소를 적용하는 방법


> AGENTS.md와 docs/guide/skill-guideline.md를 읽어라. 시험 공지와 과제 README·기존 지침을 우선하고 기존 AGENTS.md는 덮어쓰지 마라. 과제 디렉터리를 확인해 스킬을 설치하고 SKIP된 기존 스킬은 알려줘. 스킬 적용 시 시험용 조정을 우선하고, 검색되지 않으면 SKILL.md를 직접 읽어라.

## 지금 어떤 스킬을 쓸까?

| 현재 상황 | 스킬 | 기대할 결과 |
|---|---|---|
| 목표·업무 규칙·계산 기준이 불명확 | grilling | 중요한 질문과 근거가 담긴 요구사항 기록 |
| 할 일이 정해짐 | implement | 작동하는 작은 기능 |
| 핵심 규칙 검증 또는 오류 원인 조사 | test-and-debug | 독립 기대값·실패 재현·수정과 재검증 |
| 사용자 경로를 반복 확인해야 함 | create-verification-skill | 허용된 검증 절차 |
| 완성했지만 빠진 게 걱정됨 | code-review | 요구사항 및 코드 결함 목록 |
| 제출 직전 완료 여부를 확인 | verification-before-completion | 요구사항별 실제 검증 증거 |
| 속도 개선을 주장해야 함 | benchmark-checklist | 같은 조건의 비교 결과 |
| 세션을 전환해야 함 | handoff | 검증된 현재 상태와 다음 작업 |

모든 스킬을 순서대로 부를 필요는 없다. 동일한 스킬을 매번 다시 호출할 필요도 없다. 아래의 괄호 부분은 실제 과제에 맞게 바꾼다.

## 1. grilling: 목표와 업무 규칙을 확인할 때

**상황:** 업무 목표나 계산 기준·데이터 단위·상태·예외가 모호하다.

> grilling을 적용해 README와 제공 자료·기존 코드를 확인하고 목표와 업무 규칙을 정리해라. 결과를 바꾸는 질문을 최대 5개 제시하고 각각의 영향을 설명해라. 확인된 사실의 근거, 가정, 미확인 사항과 검증 기준을 과제 문서에 짧게 기록해라. 담당자에게는 내가 직접 질문한다.

**내가 확인할 것:** 질문의 답이 이미 자료에 있는지, 기록한 내용과 근거가 일치하는지 확인한다. 담당자 답변을 받은 뒤에는 같은 기록과 필요한 구현에 반영하도록 요청한다.

## 3. implement: 첫 기능을 만들 때

**상황:** 필수 범위와 첫 검증 사례가 정해졌다.

> implement로 [입력→처리→출력] 경로부터 구현해라. 기존 기술과 실행 방법을 유지하고, 정상 입력 하나가 실제로 작동하도록 검증해라. 부가 기능과 자동 커밋은 생략해라.

**내가 확인할 것:** 코드가 만들어졌다는 보고뿐 아니라 실제 입력과 출력. 무엇을 먼저 만들고 무엇을 미뤘는지 설명할 수 있어야 한다.

## 4. test-and-debug: 중요한 규칙을 검증하거나 오류를 조사할 때

**상황:** 계산·판정·상태 전이의 정확성이 중요하거나 실행 결과가 예상과 다르다.

> test-and-debug로 [기능 또는 오류]를 확인해라. 정상·경계·결측 사례의 기대값은 명세나 수계산으로 정해라. 실패가 있다면 같은 입력으로 재현하고 로그로 원인을 좁힌 뒤 최소 수정하고 다시 검증해라. 실제 결과와 미검증 항목을 구분해라.

**내가 확인할 것:** 기대값의 근거, 오류 재현과 수정 전후 결과. 구현에 맞춰 테스트를 느슨하게 바꾸지 않았는지 확인한다. 구현 전에 테스트가 실제로 실패하는 것을 보지 못했다면 검증 결과를 그대로 표현한다.

## 5. create-verification-skill: 반복 검증이 필요할 때

**상황:** 여러 번 확인할 사용자 흐름이 있고 검증 절차가 자주 흔들린다.

> create-verification-skill의 원칙으로 [핵심 흐름]의 검증 절차를 만들어라. 허용된 CLI·API 검사와 내가 브라우저에서 직접 할 조작을 분리하고, 예상 결과와 확인 증거를 적어라. Computer Use나 화면 자동 조작은 사용하지 마라.

**내가 확인할 것:** 검증 절차를 만드는 데 과제보다 많은 시간을 쓰지 않는지. 화면 입력과 클릭은 직접 하고 실제 결과를 확인한다. 짧은 분석 과제라면 별도 스킬 대신 재현 명령과 체크리스트로 충분할 수 있다.

## 6. code-review: 필수 기능을 만든 뒤

**상황:** 작동은 하지만 요구사항 누락이나 코드 오류가 걱정된다.

> code-review를 적용해 요구사항 충족과 코드 품질을 별도 관점으로 검토해라. 커밋된 변경뿐 아니라 미커밋 변경과 신규 파일도 확인하고, 제출을 막는 결함과 선택 개선을 구분해라. 병렬 기능이 없으면 순차 검토해라.

**내가 확인할 것:** 실제 필수 조건이 빠졌는지, 계산과 데이터 처리가 맞는지. 스타일 제안을 모두 고치느라 중요한 검증 시간을 쓰지 않는다. Git이 없는 작업 공간은 현재 파일과 요구사항을 직접 비교하게 한다.

## 7. verification-before-completion: 제출하기 전

**상황:** 결과물이 완료됐다는 보고를 받았고 제출을 준비한다.

> verification-before-completion으로 필수 요구사항별 구현 위치, 마지막 관련 변경 이후 실행한 검증과 실제 결과를 정리해라. 완료·실패·미검증을 구분하고, 필요한 파일 경로와 저장 상태도 확인해라.

**내가 확인할 것:** 실행하지 않은 테스트를 통과로 적지 않았는지. 빌드 통과와 실제 기능 확인을 구분하고, 최종 수정 후 영향을 받는 검사를 다시 수행한다. 화면과 최종 제출은 직접 확인한다.

## 8. benchmark-checklist: 성능을 비교할 때

**상황:** 기존 처리 방식보다 빠르다는 결과를 보고해야 한다.

> benchmark-checklist로 기존과 변경 방식을 같은 입력·환경에서 비교해라. 두 결과가 같은지와 오류 수를 확인하고, 반복 측정 횟수·중앙값·범위를 기록해라. 실행하지 못한 비교는 미검증으로 표시해라.

**내가 확인할 것:** 더 적은 데이터를 처리하거나 오류를 빨리 반환해서 빨라진 것은 아닌지. 한 번만 측정했다면 그 사실을 밝히고 일반적인 개선 효과로 단정하지 않는다.

## 9. handoff: 작업을 이어받아야 할 때

**상황:** 세션 전환이나 컨텍스트 부족으로 현재 상태를 넘겨야 한다.

> handoff를 작업 공간에 작성해라. 목표, 확정 규칙과 근거, 변경 파일, 마지막 검증 결과, 재현 가능한 실패, 시도 후 폐기한 방법, 다음 작업을 짧게 기록해라. 임시 경로가 아니라 세션 간 보존되는 경로를 사용해라.

**내가 확인할 것:** 새 세션이 문서를 실제로 읽을 수 있는지. 인계문에 적힌 내용도 새 세션에서 파일과 검증 결과를 대조해야 한다.

## 예시 흐름: 설비 기록 분석 도구

아래는 연습용 가상 과제다. 실제 출제 내용을 뜻하지 않는다.

1. README와 CSV를 읽고 원래 실행 상태를 확인한다.
2. **grilling:** 재검사와 이상 기준 등 결과를 바꾸는 질문을 준비하고, 확인된 업무 규칙과 근거·가정을 과제 문서에 기록한다. 본인이 담당자에게 직접 묻고 답변을 같은 문서에 반영한다.
3. **implement + test-and-debug:** CSV의 작은 입력 하나로 집계 결과가 나오는 경로를 만들고, 수계산 가능한 정상·경계 사례를 검증한다.
4. **test-and-debug:** 실패가 있을 때만 재현하고 수정한다.
5. 사람이 브라우저에서 직접 업로드와 표시를 확인한다. 반복 검증 절차가 필요할 때만 **create-verification-skill**을 쓴다.
6. **code-review:** 필수 조건과 신규 파일까지 확인한다. **verification-before-completion:** 최종 변경본의 실제 검증 결과를 정리한다.

이때 각 스킬은 상황에 따라 건너뛸 수 있다. 구현 결과를 자신이 이해하고 있는지 확인하기 위해 입력, 처리, 출력, 선택 이유, 테스트와 한계를 짧게 설명해 본다.

## 시간이 부족할 때

- 필수 조건을 확인하고 작동 경로 하나를 먼저 완성한다.
- 결과를 바꾸는 계산과 주요 실패 사례를 검증한다.
- 코드 리뷰에서는 필수 누락과 중대한 오류부터 확인한다.
- 마지막에는 필수 파일·저장 상태·제출 화면을 확인한다. 시험 안내상 미리보기에서도 시간이 흐르므로 여유를 둔다.
- 서술형 단계에 들어가면 AI를 사용하지 않는다. 질문의 전제가 실제 구현과 다르면 차이를 바로잡고 자신이 수행한 내용을 설명한다.
