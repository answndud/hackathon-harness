# 해커톤 과제 실전 가이드

이 문서는 최상단 README와 여러 제공 자료가 있는 과제를 단계적으로 파악하고, 핵심 판단과 검증 근거를 과제 작업 공간에 남기기 위한 응시자용 가이드다. 실제 문제·문항·채점 방식은 과제마다 다를 수 있다. 최신 시험 공지, 과제 README, 기존 지침과 제출 조건을 우선한다.

## 먼저 기억할 원칙

- **파일을 나눠 읽는다.** README로 자료의 역할과 의존 관계를 파악한 뒤, 중요한 자료부터 목적별로 나눈다. 필요한 자료를 누락하지 않도록 읽은 파일과 미확인 파일을 기록한다.
- **답변만 받지 않고 기록한다.** 목표·요구사항·자료 해석·계획·결정·검증 결과는 과제 작업 공간에 갱신하도록 요청한다. 상세 내용은 채팅에 길게 출력하지 않는다.
- **실제 근거만 남긴다.** 출처·확인된 사실·가정·미확인과 실행한 검증·계획된 검증을 구분한다. 없는 수치·경로·판단 이유를 만들지 않는다.
- **일단 필수 흐름을 완성한다.** 구현 전 중요한 제약과 데이터 계약을 확인하고, 사용자 입력부터 실제 결과까지 작동하는 최소 경로를 우선한다.
- **마지막에 설명할 수 있어야 한다.** 중요한 로직은 입력·처리·출력·제약·검증·한계를 직접 설명할 수 있도록 짧게 확인한다.

## 기록 위치

기존 과제의 요구사항·계획 문서를 우선 사용한다. 없으면 시험 규칙이 허용할 때 과제 작업 공간의 `docs/requirements.md`에 자료 목록, 요구사항과 계획을 간결하게 기록한다. 기존 파일을 덮어쓰지 말고 해당 섹션을 추가하거나 갱신한다.

여러 세션의 각 작업 보고는 [작업 기록 지침](../docs/work/README.md)에 따라 담당자가 `docs/work/<작업명>.md`에 기록한다. 중요한 미해결 문제의 상세와 최신 상태는 [부채 기록 지침](../docs/debt/README.md)을 따른다. 작업 보고에는 문제를 한 줄로 남기고 관련 부채 경로를 연결한다. 담당자가 정해진 공통 문서를 동시에 수정하지 않는다.

과제에서 별도로 요구하는 제출 문서의 위치·형식·작성 시점은 README를 따른다. 하네스 원본에는 과제 자료를 기록하지 않는다. 기록이 금지되거나 쓰기에 실패하면 사실과 경로를 알리고, 허용된 다른 과제 문서가 있으면 사용한다. 기록이 전혀 불가능할 때는 간결하게 채팅으로 전달한다. 민감 정보와 비밀 값은 기록하지 않는다.

## 스킬 선택과 시험 제한

시험 공지·과제 README와 상위 지침이 우선한다. `AGENTS.md`의 시험 제한과 아래 조정을 따르고, 스킬 원본과 충돌하면 시험용 지침을 우선한다. 과제·결과물의 외부 전송, push·PR·배포, 자동 커밋, Computer Use와 브라우저 자동 조작은 하지 않는다. 담당자 AI 대화, 브라우저 검증과 최종 제출은 응시자가 직접 한다. 후속 서술형의 AI·문서 사용은 시험 안내를 따른다.

스킬을 모두 호출할 필요는 없다. 이름을 명시하지 않아도 필요한 경우만 선택하고 `skills/<이름>/SKILL.md`와 필요한 참조를 직접 읽게 한다. 이 경로의 자동 검색은 보장되지 않는다. 설치에서 기존 파일이 SKIP되어 하네스와 다르면 원본 파일은 보존하고 최신 clone의 스킬을 직접 읽는다. 파일을 읽지 못하면 한계를 기록하고 관련 원칙을 직접 적용한다.

| 상황 | 스킬 | 적용과 확인 |
|---|---|---|
| 목표·업무 규칙이 모호 | `grilling` | 자료를 먼저 읽고 결과를 바꾸는 질문만 추려 근거·미확인과 함께 기록한다. |
| 여러 단계의 범위와 순서 정리 | `planning` | 최소 기능·의존 관계·검증을 계획하고, 개선 과제라면 변경 전 기준안과 비교 지표를 확보한다. |
| 필수 기능 구현 | `implement` | 작은 입력→처리→출력을 구현하고 핵심 처리·선택·실제 검증·한계를 설명한다. |
| 핵심 규칙 검증·오류 진단 | `test-and-debug` | 독립 기대값·경계 사례·필수 제약을 확인하고 오류는 재현·수정·재검증한다. |
| 반복 검증 절차가 필요 | `create-verification-skill` | 반복할 가치가 있을 때만 사용한다. CLI·API 검사와 응시자가 직접 수행할 화면 검증을 분리한다. |
| 요구사항 누락·품질 검토 | `code-review` | 요구사항·계산·권한·통합·실행 장애를 우선하고 미커밋·신규 파일도 확인한다. |

스킬 선택 기준은 `planning` 스킬과 Codex의 `/plan` 명령을 구분한다. 한 번의 짧은 확인에는 별도 검증 스킬보다 재현 명령과 체크리스트가 충분할 수 있다. 출력과 반복 호출은 줄이되 핵심 검증은 생략하지 않는다. 모델과 추론 수준은 환경에서 지원되는 범위에서 응시자가 선택한다.

**반복 검증 절차가 필요할 때:**

> `create-verification-skill`의 원칙으로 [핵심 흐름]의 반복 검증 절차를 과제 문서에 기록해라. 허용된 CLI·API 검사와 내가 직접 할 브라우저 조작을 구분하고 입력·기대 결과·실제 결과를 남겨라. 화면 자동 조작은 사용하지 마라.

**오류 조사·리뷰가 필요할 때:**

> [기능 또는 오류]를 명세와 실제 코드로 확인해라. 오류는 재현·근거 확인·최소 수정·재검증하고, 요구사항 누락·계산·권한·통합·실행 장애를 우선 검토해라. 실행 결과와 미검증, 수정 위치와 남은 문제를 담당 작업 문서에 기록해라.

## 1. 최상단 README로 과제 지도 만들기

과제마다 다른 필수 산출물, 제공 파일과 제출 조건을 먼저 확인한다. 마크다운 파일이 두 개 소개되더라도 각 파일이 제출물인지 참고 자료인지, 언제 무엇을 써야 하는지는 실제 README를 기준으로 확인한다.

**총괄 Codex에 입력:**

> 최상단 과제 README만 먼저 읽고 과제 목적, 사용자, 필수 산출물·요구사항·제약, 제출 조건과 실행 환경을 정리해라. README에 설명된 마크다운 문서와 CSV 등 제공 파일은 각각 실제로 확인된 역할·경로만 목록화해라. 확인된 사실에는 README 위치를 붙이고 추측과 미확인을 구분해라. 기존 과제 요구사항 문서에 기록하고 없으면 허용된 과제 공간의 `docs/requirements.md`를 만들어 기록해라. 다음에 확인할 자료를 중요도·의존 관계에 따라 묶어 같은 문서에 적어라. 아직 다른 과제 자료의 전체 분석이나 구현은 시작하지 말고 기록 경로와 핵심만 알려줘.

시험의 상위 지침이나 README가 특정 자료를 먼저 확인하도록 요구하면 그 지시를 따른다. 이 단계에서 제출 문서의 내용을 완성했다고 가정하지 않는다.

## 2. 산출물·자료 우선순위 확인

첫 기록에서 제출해야 하는 문서의 경로, 기존 파일의 존재 여부, 필수 항목과 제출 방식을 확인한다. 요구사항을 이해하기 위해 필요한 자료는 먼저 읽되, 나머지는 묶음별로 확인한다.

**Codex에 입력:**

> 과제 README를 기준으로 필수 기능·제약·제출물·검증 항목과 미확인을 요구사항 문서에 정리해라. 제출 문서가 이미 있으면 실제 파일을 확인하고 내용을 보존해라. 없다면 생성 조건과 요구 형식만 기록해라. 제공 자료별로 읽음·미확인과 확인 목적을 표시하고, 필수 판단에 필요한 자료부터 나눠 읽는 순서를 문서에 기록해라.

소감이나 풀이 문서를 개발 전에 완성하지 않는다. 구현 전에는 요구 항목만 파악하고, 실제 선택·검증·결과가 생길 때 해당 근거를 누적한다. 개인 소감은 응시자의 실제 경험을 확인받고 작성한다.

## 3. 제공 파일을 목적별로 분석

각 묶음의 크기는 파일 수가 아니라 업무 규칙·데이터 관계와 남은 시간으로 정한다. 중요한 규칙·핵심 입력·기준안·사용자 기능 자료를 우선하되 실제 순서는 README의 의존 관계에 맞춘다. 필요한 모든 자료를 최종 제출 전까지 확인한다.

**자료 묶음마다 입력:**

> 이번에는 `[파일 1]`, `[파일 2]`만 분석해라. 파일 목적, 각 행의 의미, 주요 필드·단위·시점·식별자와 필요한 결측·중복을 실제로 확인해라. 업무 규칙, 다른 파일과의 연결, 구현·검증에 미치는 영향과 미확인을 기존 과제 문서에 기록해라. 행 수·열·값은 확인한 것만 적고 전체 데이터 출력은 생략해라. 읽은 파일과 남은 파일 목록도 갱신해라.

문서에는 파일명과 시트·행·열·조항 등 실제 확인 가능한 위치를 남긴다. 행 번호는 헤더 포함 여부와 기준을 명시하고, 정확한 위치를 알 수 없다면 추측하지 않는다. 유용한 결과만 출력한다.

**자료 묶음을 연결할 때:**

> 지금까지 읽은 자료를 대조해 연결 키·단위·시점·업무 규칙의 일치 여부와 충돌, 가정·미확인을 과제 문서에 갱신해라. 아직 읽지 않은 필수 자료를 표시하고, 결과를 바꾸는 질문과 각 답변의 영향을 문서에 기록해라.

## 4. 업무 담당자에게 확인

자료로 해결되지 않는 질문 중 구현을 바꾸는 항목만 고른다. 담당자 AI와의 대화는 응시자가 직접 한다. 답변도 제공 자료와 비교하며, 충돌하거나 모호하면 재확인한다.

**질문 준비:**

> 제공 자료와 과제 문서를 대조해 결과를 바꾸는 미확인 질문을 우선순위대로 최대 3개 작성하고, 각 답변이 구현에 미칠 영향을 과제 문서에 기록해라. 내가 담당자에게 직접 전달한다.

**답변을 받은 뒤:**

> 아래 담당자 답변을 기존 자료와 대조해 요구사항 문서의 규칙·출처·적용 범위와 검증 기준을 갱신해라. 충돌·남은 가정은 표시하고, 확인되지 않은 사항을 확정하지 마라. 답변을 기다리는 동안 진행 가능한 독립 작업도 계획에 기록해라.

## 5. 구현 계획과 기준안

과제에 필요한 최소 사용자 흐름, 필수 제약과 검증을 먼저 정한다. 기존 방식의 개선이 요구되거나 개선을 주장하려면 변경 전 기준안의 자료·코드·실행 조건을 보존하고, 비교 지표를 정한다. 기존안이 없거나 실행이 불가능하면 한계를 기록한다.

**Codex에 입력:**

> 확인된 README와 자료로 필수·보류 범위, 최소 입력→처리→출력 흐름, 필수 제약, 단계별 작업·의존 관계와 검증을 기존 과제 문서에 기록해라. 개선 과제면 변경 전 기준안·데이터·실행 방법·비교 지표를 확인하고, 비교가 불가능한 부분도 기록해라. 필요한 경우 핵심 로직·백엔드·프론트엔드의 경계와 공통 계약, 작업 보고서 경로를 정해라. 통합·검증·응시자 이해·제출 시간을 남기고, 미확인은 가정으로 표시해라.

## 여러 세션을 사용할 때

시험 환경에서 여러 터미널·세션이 허용되는지 먼저 확인한다. 허용되지 않거나 작업이 작으면 한 세션에서 순차적으로 진행한다. 역할을 고정 인원수로 여기지 말고 독립성·시간·토큰·조정 비용에 따라 합치거나 생략한다.

| 역할 | 담당할 작업 |
|---|---|
| 총괄·통합 | 목표·제약·공통 계약·파일 소유권과 작업 보고 경로를 정하고 결과를 통합한다. |
| 핵심 로직·데이터 | 자료와 규칙을 확인하고 계산·판정·최적화, 제약과 기준안 비교를 맡는다. |
| 백엔드 | 필요한 API·서버 검증·권한·저장·조회와 핵심 로직 연결을 맡는다. |
| 프론트엔드 | 필요한 화면·상태·API 연결을 맡고 응시자의 수동 확인 절차를 기록한다. |
| 독립 검증 | 명세·수계산의 기대값으로 핵심 규칙과 제약·통합 결과를 확인한다. |

총괄은 구현 전에 필요한 데이터 식별자·단위·결측 처리, 핵심 로직의 입력·출력, API 요청·응답·오류, 저장 방식과 화면 상태를 합의해 과제 문서에 기록한다. 아직 미정인 규칙은 가정으로 표시한다. 백엔드와 핵심 로직의 연결 책임자를 한 명 정한다.

같은 작업 폴더의 세션은 파일을 공유하지만 서로의 대화는 자동 공유하지 않는다. 각 세션에 담당 경로·공통 계약·보고서 경로를 응시자가 전달한다. 공통 설정·타입·스키마·의존성은 수정 책임자를 한 명으로 정하고, DB·서버 포트·마이그레이션도 충돌하지 않게 조정한다. 다른 세션의 파일을 임의로 덮어쓰거나 되돌리지 않는다. worktree 등 별도 작업 공간에서는 수정과 보고서가 자동 공유되지 않으므로 허용 여부·접근·제출 경로와 통합 비용을 확인한다.

각 작업 세션은 [작업 기록 지침](../docs/work/README.md)에 따라 자신의 `docs/work/<작업명>.md`만 갱신한다. 총괄 또는 추적 세션은 **요청받을 때** 실제 파일과 검증 근거를 대조하고 중요한 문제만 [부채 지침](../docs/debt/README.md)에 따라 관리한다. 자동 감시나 세션 간 자동 메시지는 가정하지 않는다. 계약 변경과 부채 경로는 응시자가 관련 세션에 전달한다.

**총괄 세션에 입력:**

> 과제와 기존 환경을 확인하고 필요한 작업만 핵심 로직·백엔드·프론트엔드·검증으로 나눠라. 세션별 담당 파일·입출력 계약·의존 관계·작업 보고서·통합 검증을 과제 문서에 기록해라. 독립 작업만 동시에 진행하고, 내가 각 세션에 전달할 요청도 기록해라.

각 역할별 요청에는 담당 경로와 공통 계약을 넣고 해당 문서에 기록하도록 한다.

- **핵심 로직:** 자료·필수 규칙·제약을 확인하고 계산을 구현한다. 기준안과 비교가 필요하면 변경 전에 보존하고 독립 기대값으로 검증한다.
- **백엔드:** 합의된 API·서버 검증·필요한 권한·저장·조회를 구현하고 실제 요청·응답과 저장 후 조회를 확인한다.
- **프론트엔드:** 합의된 API로 사용자 흐름과 필요한 로딩·빈 결과·오류를 구현한다. 임시 데이터 여부와 응시자의 수동 검증 절차를 기록한다.
- **독립 검증:** 구현과 독립된 명세·수계산 기대값으로 정상·경계·실패 사례와 제약·통합을 대조한다. 미실행 검사를 통과로 쓰지 않는다.

**작업 세션에 입력:**

> [담당 경로]에서 [담당 작업]을 [공통 계약]에 따라 진행해라. 실제 변경 파일·선택·실행한 검증과 결과·미해결을 배정된 작업 보고서에 기록해라. 담당 외 공유 파일 변경이 필요하면 작업 보고서에 남겨라.

**추적·통합 세션에 입력:**

> 작업 보고서와 실제 파일·검증 근거를 대조해 공통 계약의 불일치, 임시 데이터, 중요한 미해결 부채와 다른 세션에 전달할 내용을 과제 문서에 기록해라. 변경을 통합한 뒤 실제 사용자 흐름과 마지막 관련 변경의 영향 범위를 다시 검증하고 실제 결과·미검증을 기록해라.

## 6. 구현하면서 근거와 제출 문서 갱신

각 작업은 실제 데이터와 확정된 규칙을 적용하고, 중요한 결정과 실행 결과를 담당 작업 기록에 남긴다. 단일 세션이나 작은 과제는 기존 과제 문서를 재사용한다.

**구현 작업마다 입력:**

> `[필수 작업]`을 합의된 범위와 계약에 맞춰 구현하고 필요한 검증을 실행해라. 선택 이유, 실제 구현 파일·함수, 검증 입력·기대값의 근거·명령·실제 결과와 한계를 담당 작업 문서에 갱신해라. 중요한 문제는 한 줄로 남기고 부채 지침의 담당자에게 전달해라. 실제로 확인한 중요한 AI 제안은 대조 근거와 채택·수정·기각 결과를 기록해라.

**기준안 비교가 필요한 경우:**

> 기존안과 변경안을 같은 데이터·조건·제약·산식으로 평가하고 실제 지표와 위반·누락 여부, 실행 방법과 결과 위치를 과제 문서에 기록해라. 미측정·조건 차이와 한계를 표시하고 근거 없는 개선·최적성 주장을 하지 마라.

제출 문서에는 README가 요구하는 내용을 실제 근거에 맞춰 반영한다. 구현하지 않은 기능, 실행하지 않은 검사, 검토하지 않은 대안을 꾸며 쓰지 않는다. 중요한 처리 흐름은 응시자가 코드 없이 설명할 수 있도록 짧게 설명받는다.

중요한 계산·설계와 통합이 끝날 때 응시자가 처리 흐름·선택·실제 검증·한계를 직접 설명해 본다. 캐시·성능·저장·권한처럼 실제로 사용한 부분의 확인 질문과 Codex 요청은 [문제 해결 가이드의 이해 확인](problem-solving-guide.md#서술형을-위한-이해-확인)을 따른다.

## 7. 통합·최종 점검

요구사항별 구현 위치, 실제 실행 증거, 작업 보고서와 중요한 부채를 대조한다. API·데이터·사용자 화면이 필요한 과제라면 통합된 흐름을 확인한다. 최종 변경 뒤 영향받는 검사를 다시 수행한다. 화면 확인과 제출은 응시자가 직접 한다.

**Codex에 입력:**

> 과제 README의 필수 요구사항·제출물과 실제 구현을 대조해라. 각 항목의 구현 위치와 마지막 변경 후 실행한 검증·실제 결과를 기존 과제 문서에 정리하고 완료·실패·미검증을 구분해라. `docs/work/` 보고서와 중요한 미해결 부채를 확인해 남은 위험·다음 조치를 기록해라. 제출용 문서의 형식·경로·내용을 확인하고, 내가 직접 수행할 화면 확인 절차와 예상 결과도 기록해라. 최종 제출은 내가 직접 한다.

서술형에서 AI 사용이나 문서 열람이 가능한지는 최신 시험 안내를 따른다. 사용이 제한된다면 구현 중에 핵심 선택, 실제 검증, 파일 위치와 한계를 이해해 둔다. 결과가 입증되지 않았다면 질문의 전제도 그대로 받아들이지 않는다.

## 빠른 재개 요청

방향이 흐려지거나 세션을 이어받을 때 다음 요청으로 현재 상태를 문서에 갱신한다.

> 과제 README, 기존 요구사항 문서, 필요한 작업 보고·부채 기록과 실제 파일을 대조해 필수 목표, 완료·실패·미검증, 가장 중요한 막힌 지점과 다음 작업 하나를 과제 문서에 갱신해라. 보고된 검증과 직접 확인한 검증을 구분하고 핵심과 문서 경로만 알려줘.
