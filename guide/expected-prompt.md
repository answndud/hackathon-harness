# 과제 진행할 때 사용할 프롬프트

## 문제 파악 → 자료 확인 → 규칙 정리 → 도메인 질문 → 구현 방식 결정 → 작은 예제로 검증 → 구현 → 독립 검증 → 제출 및 설명 준비

아래 프롬프트를 순서대로 사용하되, 과제에서 요구하지 않는 단계는 건너뛰면 돼. 예를 들어 기준안과 개선안을 비교하는 과제가 아니라면 해당 프롬프트는 사용할 필요 없어. 문서 경로와 항목도 예시니까 실제 과제의 제출 규칙이나 기존 프로젝트 구조에 맞게 바꿔서 사용해.

각 단계는 시험·과제 지침과 기존 기록을 우선해. 별도 지시나 같은 역할의 기존 문서가 없고 쓰기가 허용되면 아래 경로를 과제 작업 공간에서 사용해. 아래 입력 경로는 기본값이야. 기존 문서를 사용한 경우에는 그 실제 경로를 확인해 대신 읽고, 해당하지 않아 건너뛴 단계의 파일은 요구하거나 임의로 만들지 마. 필요한 근거가 누락됐다면 원본에서 확인하고, 확인할 수 없으면 미확인으로 남겨줘. 번호는 단계에 고정하고 건너뛴 단계의 파일은 만들지 않아. 이미 파일이 있으면 내용을 보존하고 해당 내용을 갱신해. 실제 과제 내용을 하네스 원본에 기록하지 마.

## 작업 시작 전

과제를 시작하기 전에 현재 작업 공간에 적용되는 `AGENTS.md`와 과제 지침을 확인해줘. 이미 시작된 세션에서 나중에 추가된 지침은 자동으로 읽었다고 가정하지 마. 아래 프롬프트는 필요한 단계만 골라 사용하고, 기존 과제 문서와 기록 방식을 우선해줘.

## 2. 자료와 기존 구현 확인

README와 `docs/01-problem-map.md`에 언급된 파일들을 읽고 어떤 자료가 있는지 파악해줘. 원본은 수정하지 말고 결과를 `docs/02-data-map.md`에 정리해줘.

- 파일별 용도, 형식, 출처와 생성 시점
- 각 파일이 어떤 요구사항을 해결할 때 필요한지
- 데이터의 주요 컬럼, 단위, 기간, 식별자와 파일 간 연결 관계
- 데이터가 갱신되는 기준이나 시점이 있는지
- 누락값, 중복, 형식 오류, 파일 간 불일치 등 확인한 품질 문제
- 문서, 표, 이미지 등에서 내용을 제대로 추출하지 못했을 가능성이 있는 부분
- 기존 코드가 있다면 현재 구현된 기능과 실행 방법, 아직 확인하지 못한 부분
- 과제에서 허용한 실행 환경에서 필요한 도구와 의존성을 사용할 수 있는지, 확인하지 못한 제약은 무엇인지

데이터 건수나 품질을 적을 때는 전체를 확인한 결과인지 일부만 확인한 결과인지, 어떤 방법으로 확인했는지도 적어줘. 데이터 연결에 필요한 값이 없거나 연결 기준이 모호하면 임의로 채우지 말고 따로 표시해줘. 개인정보나 긴 원문은 불필요하게 옮겨 적지 마.


## 3. 규정과 처리 조건 정리

README에서 확인한 규정, 제한사항과 관련 파일들을 읽고 정리해줘. 아래 항목은 예시니까 실제 과제에 맞게 수정해서 `docs/03-policy.md`에 작성해줘. `docs/01-problem-map.md`와 `docs/02-data-map.md`도 참고해줘.

- 규칙이 적용되는 대상과 조건
- 기준값, 단위, 경계값과 예외
- 필요한 입력값과 입력이 없을 때 처리 방법
- 조건을 만족하거나 만족하지 못했을 때의 결과와 후속 처리
- 상태값이 있다면 각 상태의 의미와 상태가 바뀌는 조건
- 날짜 제한, 처리 순서, 제출 또는 기록 양식이 있는지
- 근거 파일과 조항 또는 해당 위치
- 해석이 모호하거나 서로 충돌하는 부분

반드시 지켜야 하는 조건과 가능한 한 개선하고 싶은 목표를 나눠줘. 규정에 없는 기준은 만들지 말고 미확인으로 표시해줘. 기존 코드의 동작과 문서에 적힌 규정이 다르다면 둘을 같은 것으로 취급하지 말고 차이를 적어줘.

규정이 별도로 없는 과제라면 억지로 만들지 말고 요구사항과 결과물을 판단할 기준을 중심으로 정리해줘.


## 4. 도메인 담당자에게 질문하기

현재까지 분석한 요구사항, 자료 구조, 규칙을 바탕으로 부족한 도메인 지식을 담당자 또는 도메인 담당자 AI에게 질문할 거야.

`docs/01-problem-map.md`, `docs/02-data-map.md`, `docs/03-policy.md`와 관련 원본을 읽고 다음을 구분해줘.

- 확인된 사실: 실제 문제나 제공 자료에서 확인한 내용과 근거
- 가정: 구현이나 분석을 진행하기 위해 임시로 정한 내용
- 미확인: 담당자나 추가 자료를 통해 확인해야 하는 내용

가정과 미확인 내용 중 결과나 구현 방식에 영향을 크게 주는 것부터 질문지 형태로 `docs/04-domain-questions.md`에 작성해줘. 기존 질문지가 있다면 해당 파일을 사용하고 원래 내용을 보존해줘. 자료에서 이미 답을 찾을 수 있는 내용은 먼저 확인하고, 질문은 내가 그대로 복사해서 담당자에게 물어볼 수 있도록 구체적으로 작성해줘. 질문에 필요한 상황이나 조건도 질문 안에 포함해줘.

내가 각 질문을 직접 복사해서 물어본 뒤 답변을 다시 파일에 붙여넣을 거야. 아래 양식을 그대로 사용하고, 답변을 받기 전에는 답변 칸을 비워둬. 확인이 필요한 이유나 현재 근거는 질문과 답변을 복사하는 데 방해가 되지 않도록 질문지 아래에 별도로 정리해줘.

```text
[질문 1]
질문: ...
답변:

[질문 2]
질문: ...
답변:
```

### 답변을 파일에 채운 후

앞에서 사용한 질문지(기본 경로 `docs/04-domain-questions.md`)에 내가 직접 붙여넣은 답변을 읽고 기존 규정 및 문제 요구사항과 대조해줘. 답변이 비어 있는 질문은 아직 답변을 받지 못한 것으로 표시하고, 네가 답을 만들어 채우지 마.

답변을 통해 확인된 내용과 그 내용이 영향을 주는 규칙이나 구현 방식을 정리해줘. 기존 자료와 충돌하지 않고 충분히 명확한 답변은 해당하는 `docs/01-problem-map.md`, `docs/02-data-map.md`, `docs/03-policy.md`에 반영하되, 근거를 실제 질문지의 해당 질문과 답변으로 남겨줘. 답변이 모호하거나 기존 자료와 충돌하면 확정하지 말고 추가 확인 사항으로 남겨줘.

도메인 담당자 AI의 답변도 공식 규정과 같은 것으로 자동 취급하지 말고, 답변의 출처와 확인 범위를 표시해줘. 질문과 내가 붙여넣은 답변 원문은 유지해줘.


## 5. 해결 방식과 검증 기준 정하기

현재까지 확인한 요구사항, 자료, 규정과 담당자 답변을 바탕으로 어떻게 문제를 해결할지 정리해줘. 아직 확정되지 않은 내용을 확정된 것처럼 구현하지 않도록 `docs/01-problem-map.md`부터 `docs/04-domain-questions.md`까지 필요한 문서를 읽고 `docs/05-solution-plan.md`에 아래 내용을 작성해줘.

- 최종 결과물과 핵심 사용자 흐름
- 어떤 입력을 받아 어떤 처리를 거쳐 어떤 결과를 만드는지
- 반드시 지켜야 할 조건과 예외, 입력 누락이나 처리 실패 시 대응
- 고려할 수 있는 해결 방식과 각각의 장단점
- 선택한 방식과 그 이유, 선택하지 않은 방식의 이유
- 결과가 올바른지 확인할 방법과 필요한 데이터 또는 근거
- 작업 순서와 의존 관계, 제한 시간 안에 먼저 완성해야 할 범위
- 확인된 실행 환경, 설치·인터넷·외부 API 제한과 실행 시간을 고려했을 때 선택한 방식을 실제로 사용할 수 있는지
- 아직 확인하지 못한 내용과 임시 가정이 결과에 미치는 영향

규칙이나 계산식이 필요한 과제라면 조건, 결과, 필요한 입력, 경계값, 예외와 근거를 정리하고 사람이 직접 계산해볼 수 있는 예시도 만들어줘. 수치로 비교할 지표가 있다면 계산식, 단위, 분자와 분모, 제외 조건, 실제로 계산 가능한지까지 적어줘.


## 6. 기준안 확인 및 재현

먼저 과제 README, `docs/01-problem-map.md`, `docs/02-data-map.md`, `docs/03-policy.md`, `docs/05-solution-plan.md`와 기존 처리 방식·결과의 원본 자료를 확인해줘.

기존 방식이나 기준 결과와 비교해야 하는 과제라면 이 단계를 진행해줘. 비교가 필요 없는 과제라면 건너뛰어도 돼.

제공된 기존 처리 방식과 결과를 먼저 확인하고 `docs/06-baseline.md`에 아래 내용을 정리해줘.

- 기존 방식의 입력, 처리 순서와 결과
- 제공된 기존 결과가 있다면 생성 시점과 대상 범위
- 기준안과 개선안을 비교할 수 있는 지표와 계산식
- 공정한 비교를 위해 동일하게 맞춰야 할 데이터, 기간과 조건
- 기존 자료만으로 알 수 없는 사항과 확인이 필요한 부분

### 기준안을 확인한 후: 재현

`docs/06-baseline.md`와 관련 원본 자료를 다시 확인하고 재현 결과도 같은 파일에 갱신해줘. 변경 전에 코드 식별자 또는 허용된 사본, 입력 데이터, 설정, 실행 명령과 실제 결과를 확인 가능한 형태로 보존해줘. 자동 커밋은 하지 마. 기존 방식이 충분히 명확하면 같은 원본 데이터를 입력받아 결과를 다시 만들 수 있도록 재현해줘. 실행 방법, 처리 건수와 제외 건수, 제외 이유, 출력 위치를 기록해줘.

기존 방식이 불명확하다면 임의로 만든 방식을 실제 기존 방식이라고 표현하지 마. 비교에 사용할 단순 기준안을 제안할 수는 있지만 그것이 새로 정한 기준임을 표시하고 한계와 근거 부족 사항을 기록해줘. 기준안의 결과가 정답이라는 보장은 없으니 정답 데이터가 있는지도 별도로 확인해줘.


## 7. 작은 예제와 기대 결과 준비

먼저 과제 README, `docs/01-problem-map.md`, `docs/03-policy.md`, `docs/05-solution-plan.md`와 관련 원본 규칙을 확인해줘. 데이터 구조가 필요하면 `docs/02-data-map.md`를, 기준안을 작성했다면 `docs/06-baseline.md`도 확인해줘.

전체 데이터나 실제 흐름에 적용하기 전에 핵심 규칙과 계산을 검증할 수 있는 작은 예제를 준비할 거야. 사람이 직접 계산하거나 결과를 확인할 수 있을 정도로 작은 입력을 만들어줘.

과제에 맞게 정상 사례, 경계값, 입력 누락, 중복, 예외 상황을 골라줘. 먼저 각 사례의 입력과 기대 결과, 왜 그 결과가 나와야 하는지 근거를 적어줘. 예제 데이터와 실제 데이터는 구분해줘. 가능하면 나중에 구현할 함수와 별도로 기대값을 계산하거나 손으로 확인한 값을 명시해줘.

기존에 실행할 수 있는 코드가 있다면 실제 결과를 기대 결과와 비교해줘. 아직 구현이 없다면 실행 결과를 만들어 내지 말고 미실행으로 남겨줘. 8번에서 최소 로직을 구현한 후 이 예제를 실행하고 결과를 다시 기록할 거야.

AI가 생성한 답변이나 콘텐츠가 핵심인 과제라면, 과제에 맞게 근거에 없는 내용을 묻는 경우, 자료에 답이 없는 경우, 비슷한 질문을 다른 표현으로 하는 경우도 예제에 포함해줘. 검색을 사용한다면 관련 자료를 찾지 못하거나 관련 없는 자료가 반환되는 경우도 확인해줘. 각 사례에서 무엇을 좋은 결과로 볼지와 그 이유를 먼저 적고, 정답이 하나로 정해지지 않는 평가는 판단 기준과 한계를 밝혀줘.

예제 입력, 기대 결과와 근거, 실행 여부와 실제 결과, 검증하지 못한 항목을 `docs/07-example-verification.md`에 기록해줘. 숫자 계산이나 알고리즘이 없는 과제라면 핵심 산출물의 작은 샘플과 검토 기준을 준비해줘.

## 8. 핵심 로직 구현 또는 산출물 작성

먼저 과제 README와 `docs/01-problem-map.md`, `docs/02-data-map.md`, `docs/03-policy.md`, `docs/04-domain-questions.md`, `docs/05-solution-plan.md` 중 관련 문서와 `docs/07-example-verification.md`를 확인해줘. 기준안을 작성했다면 `docs/06-baseline.md`도 확인하고 기존 코드와 원본 자료를 대조해줘.

이 단계는 과제의 핵심 문제를 해결하는 작업이야. 데이터 처리나 알고리즘이 필요한 과제라면 그 로직을 구현하고, 분석이나 콘텐츠 작성이 중심인 과제라면 필요한 결과물을 작성해줘. 웹사이트 제작은 아래의 별도 프롬프트를 사용해서 다른 세션에서 병행할 수 있어.

기존 프로젝트의 구조와 실행 방법을 확인하고, 7번의 작은 예제에서 정한 독립 기대 결과를 유지해줘.

필수 요구사항을 만족하는 가장 작은 동작부터 구현하고 점차 완성해줘. 최소 로직을 만든 후에는 7번의 예제를 실행해 기대 결과와 실제 결과를 비교하고 `docs/07-example-verification.md`의 작은 예제 검증 기록을 갱신해줘. 실패하면 재현 방법과 확인된 원인을 기록하고 수정 후 같은 예제를 다시 실행해줘. 원인을 확인하지 못했다면 추측을 확정된 원인처럼 적지 마. 아래 항목은 예시니까 실제 과제에 맞게 적용해줘.

- 어떤 입력을 받아 어떤 순서로 처리하고 어떤 결과를 반환하는지 구현
- 필수 조건, 경계값, 입력 누락과 처리 실패 시 대응
- 결과가 만들어진 이유를 설명할 수 있도록 필요한 근거와 상태 기록
- 웹이나 다른 구성 요소와 연결해야 한다면 합의한 입력·출력 계약 준수
- 임시 가정이나 예제 데이터가 사용된 위치와 실제 데이터로 교체할 방법 기록

웹이나 다른 구성 요소와 연결해야 한다면 기존 입력·출력 계약이 있는지 먼저 확인해줘. 계약이 없고 연결에 필요하다면 필요한 범위에서 정리하고, 확정되지 않은 항목은 표시해줘. 다른 세션과 병행한다면 담당 범위를 구분하고 계약 변경 이유와 영향을 기록해 다른 세션에도 전달할 수 있도록 정리해줘.

구현 중 요구사항과 충돌하거나 중요한 판단이 필요한 부분이 생기면 영향과 가능한 대안을 정리하고, 답변과 무관하게 진행할 수 있는 작업은 계속해줘. 변경한 내용, 실행 방법, 검증 결과와 남은 문제는 `docs/08-core-implementation.md`에 정리해줘. 후속 조치가 필요한 중요한 기술 부채는 기존 과제의 관리 방식이나 `docs/debt/README.md`에 따라 관리해줘. 작업 중에도 중요한 부채를 계속 확인하고 필수 기능이나 결과의 정확성을 해치는 문제는 통합을 기다리지 말고 우선 해결·검증해줘. 담당 단계 문서에는 문제와 해당 부채 파일 경로만 짧게 연결해줘. 해결한 항목은 실제 수정과 검증 결과를 기록하고 지침에 따라 상태를 갱신해줘.

### 개선안을 비교해야 하는 경우

문제에서 개선안을 요구한다면 가능한 접근법들을 검토하고 과제의 시간과 요구사항에 맞는 방법을 선택해줘. 여러 방법을 구현하는 것이 실제로 유용한지도 먼저 판단해줘. 각 방법을 선택하거나 제외한 이유, 필요한 데이터와 제약, 설명과 검증이 가능한지를 기록해줘.

필수 조건을 먼저 확인하고 그다음 개선 목표를 비교해줘. 점수나 가중치가 필요하다면 어떻게 정했는지 근거를 남기고, 가중치가 달라질 때 선택이 바뀌는지도 가능한 범위에서 확인해줘. 증명하지 못한 결과를 최적해라고 표현하지 마.


# 웹사이트 제작

웹 서비스가 필요한 과제라면 아래 프롬프트를 순서대로 사용해. 한 세션에서 진행해도 되고 다른 작업과 병행해도 돼. 기존 웹사이트나 문서가 있다면 새로 만들기 전에 먼저 확인하고, 과제의 규모에 비해 불필요한 단계는 건너뛰어도 돼.

## 웹 1. 요구사항과 사용자 흐름 정리

먼저 과제 README, `docs/01-problem-map.md`, `docs/05-solution-plan.md`와 필요한 경우 `docs/02-data-map.md`, `docs/03-policy.md`, `docs/04-domain-questions.md` 및 기존 웹 코드를 확인해줘.

이제 웹 서비스를 구현할 거야. 과제 README와 지금까지 문서화한 요구사항, 데이터 구조, 규칙, 구현 계획을 먼저 읽어줘. 기존 웹 코드나 핵심 처리 로직이 있다면 현재 상태와 실행 방법도 확인해줘. 아직 화면이나 API를 구현하지 마.

지금까지 확인한 내용을 바탕으로 `docs/web/01-requirements.md`에 아래 내용을 정리해줘. 과제에서 문서 위치를 지정했거나 기존에 같은 역할의 문서가 있다면 그 위치를 사용해줘.

- 해결할 문제와 웹 서비스의 목적
- 누가 어떤 상황에서 사용하는지, 필요한 경우 사용자별 역할과 접근 범위
- 사용자가 처음 접속해서 입력하고 결과를 확인하기까지의 주요 흐름
- 필수 기능과 선택 기능, 화면별 입력과 보여줘야 할 결과
- 핵심 처리 로직과 연결해야 하는 부분, 데이터와 권한 요구사항
- 입력 누락, 처리 실패, 결과가 없는 경우 어떻게 안내할지
- 아직 확인되지 않은 사항과 임시 가정, 요구사항별 완료 기준

실제로 확인한 요구사항과 네가 제안한 내용을 구분해줘. 과제에 없는 역할이나 기능을 임의로 필수라고 정하지 마. 다른 세션에서 작업하고 있다면 현재까지 확인한 내용을 읽되, 정해지지 않은 내용은 미확인으로 남겨줘.

## 웹 2. 데이터와 API 계약 정리

먼저 `docs/web/01-requirements.md`, `docs/05-solution-plan.md`의 공통 계약과 관련 코드, 필요하면 `docs/02-data-map.md`와 `docs/03-policy.md`를 확인해줘.

기존 웹 요구사항 기록, 기존 코드와 핵심 로직을 확인하고 화면과 처리 로직을 어떻게 연결할지 정리해줘. 화면과 백엔드가 서로 다른 결과 구조를 가정하지 않는 것이 중요해.

먼저 기존 데이터 구조나 API 계약이 있는지 확인해줘. 있다면 실제 구현과 일치하는지 검토하고, 없다면 필요한 범위에서 계약 초안을 작성해줘. `docs/05-solution-plan.md`의 공통 계약을 기준으로 `docs/web/02-api-contract.md`에 웹 관련 세부사항을 기록해줘. 공통 계약 변경은 책임자에게 요청하고 응시자가 다른 세션에 전달해줘.

과제에 필요한 항목에 한해 입력과 출력 필드, 자료형, 상태값, 오류 응답, 사용자 권한, 요청과 응답 예시를 정리해줘. 어떤 화면이 어떤 결과를 사용하는지도 연결해줘. 확정된 내용과 임시 가정, 미확인 사항을 구분하고 근거를 남겨줘. 아직 구현하지 말고 다른 세션과 공유하거나 확인해야 할 사항을 알려줘.

## 웹 3. 구현 계획 세우기

먼저 `docs/web/01-requirements.md`, `docs/web/02-api-contract.md`, `docs/05-solution-plan.md`와 기존 프로젝트 구조를 확인해줘.

기존 웹 요구사항 기록, 데이터와 API 계약, 기존 프로젝트 구조를 바탕으로 웹 구현 계획을 세워줘. 결과는 `docs/web/03-implementation-plan.md`에 작성해줘.

- 필수 사용자 흐름을 먼저 완성하기 위한 작업 순서
- 각 작업의 담당 범위와 수정할 파일, 선행 작업
- 화면, API, 핵심 로직을 연결하는 순서
- 각 작업의 완료 조건과 확인 방법
- 임시 데이터가 필요하다면 실제 결과로 교체할 시점
- 구현 중 확인이 필요한 항목과 예상되는 기술 부채

병렬 작업이 적합하다면 각각의 서브에이전트가 맡을 범위, 공유 계약과 통합 순서를 계획해줘. 같은 파일을 동시에 수정하지 않도록 주의해줘. 병렬 작업이 불필요하거나 사용할 수 있는 서브에이전트가 없다면 순차적으로 진행할 계획을 세워줘. 이 단계에서는 계획만 작성하고 구현은 시작하지 마.

## 웹 4. 필수 사용자 흐름 구현

먼저 `docs/web/01-requirements.md`, `docs/web/02-api-contract.md`, `docs/web/03-implementation-plan.md`, `docs/05-solution-plan.md`의 공통 계약과 기존 코드를 확인해줘.

기존 웹 요구사항 기록, 계약과 구현 계획을 다시 확인하고 필수 사용자 흐름부터 구현해줘. 기존 프로젝트가 있다면 구조와 기술을 먼저 활용해줘.

사용자가 입력하고 처리 결과를 확인하는 흐름이 끝까지 연결되도록 만들어줘. 과제에서 권한이 필요하다면 사용자별 접근 범위를 적용하고, 입력 누락이나 오류, 결과가 없는 경우도 처리해줘. 아직 사용할 수 없는 로직을 임시 결과로 대체한다면 실제 결과와 구분하고 사용한 위치를 기록해줘.

작업 중 발견한 중요한 기술 부채는 기존 과제의 관리 방식이나 `docs/debt/README.md`에 따라 관리해줘. 구현 중에도 부채를 확인하고 필수 흐름이나 결과의 정확성을 막는 문제는 통합 단계까지 미루지 말고 수정하고 검증해줘. 변경 위치, 실행 방법, 실제 검증 결과와 미완료 일반 작업은 `docs/web/04-implementation.md`에 남기고 관련 부채 경로를 연결해줘. 계약이나 요구사항을 바꿔야 할 필요가 생기면 이유와 영향을 정리하고 공통 문서 책임자에게 변경을 요청해줘. 승인된 계약과 관련 구현을 함께 갱신해줘. 다른 세션과 병행한다면 변경 내용을 전달할 수 있도록 기록해줘.

## 웹 5. 실제 로직 연결과 사용자 흐름 검증

허용된 명령과 테스트로 API와 핵심 로직을 확인하고, 브라우저에서 내가 직접 확인할 핵심 사용자 흐름과 단계별 기대 결과를 안내해줘. 필요한 경우 역할별 접근, 입력 오류, 처리 실패와 결과가 없는 경우도 포함해줘. 내가 전달한 관찰 결과를 실제 처리 결과와 대조하되, 직접 보지 못한 화면은 미확인으로 남겨줘. Computer Use와 브라우저 자동화 도구로 화면을 조작하지 마.

실행 방법과 실제 결과, 실패와 미검증 항목을 `docs/web/05-flow-verification.md`에 기록해줘. 문제가 발견되면 확인된 원인과 영향을 정리하고 수정한 뒤 같은 흐름을 다시 실행해줘. 후속 조치가 필요한 중요한 미해결 문제는 기존 과제의 부채 기록 방식이나 `docs/debt/README.md`에 따라 관리해줘.


## 9. 기준안과 개선안 비교

먼저 과제 README, `docs/05-solution-plan.md`, `docs/06-baseline.md`, `docs/08-core-implementation.md`와 실제 입력·설정·실행 결과를 확인해줘. 작은 예제의 조건이 필요하면 `docs/07-example-verification.md`도 확인해줘.

비교가 필요한 과제라면 전체 데이터에 적용하기 전 작은 범위에서 기준안과 개선안을 실행하고 결과가 예상대로 나오는지 확인해줘. 이후 전체 범위에 적용할 수 있다면 동일한 대상과 조건으로 비교해줘.

`docs/06-baseline.md`와 실제 결과를 확인하고 `docs/09-comparison.md`에 비교 결과를 기록하고 다음을 포함해줘.

- 비교에 사용한 데이터 버전, 대상, 기간, 제약과 실행 조건
- 각 방식의 처리 건수와 제외 건수, 제외 이유
- 확정된 지표의 계산식, 단위와 실제 값
- 결과가 달라진 대표 사례 최대 3개와 각각의 입력, 결과, 차이가 생긴 이유와 근거
- 비교 조건이 완전히 같지 않다면 그 차이와 결과에 미치는 영향
- 결과를 해석할 때 주의할 점과 아직 확인하지 못한 내용

정답 데이터가 없으면 정확도나 오탐률을 임의로 계산하지 마. 측정하지 않은 실제 업무 시간 절감이나 사용자 만족도 개선도 확인된 성과처럼 주장하지 마. 데이터가 부족하거나 조건이 달라 비교할 수 없는 항목은 이유를 적어줘.

## 11. 최종 제출과 본인 이해 정리

### 11-1. 최종 제출물과 실제 구현 확인

과제 README와 현재 프로젝트를 다시 대조해서 제출 준비를 진행해줘. 실제 파일과 실행 결과를 확인하고 `docs/11-project-explanation.md` 또는 위에서 확인한 기존 문서의 제출 확인 섹션에 아래 내용을 정리해줘.

- 필수 제출 파일과 요구사항별 충족 여부, 확인할 수 있는 근거 위치
- 다른 사람이 그대로 따라 할 수 있는 실행 방법과 필요한 환경 설정

- 기준안과 개선안을 비교했다면 실제 차이와 비교 조건, 결과와 한계
- 구현 중 선택한 방식과 그 이유, 고려했던 대안과 절충점
- 오류·예외·권한 등 과제에서 중요한 조건과 실제 처리 방식
- 기존 부채 기록을 확인한 미해결·미검증 항목과 현재 경로, 제출 전 해결이 필요한 항목

### 11-2. 구현과 선택 과정 이해하기

11-1에서 사용한 문서와 실제 코드, 데이터, 테스트 결과, 작업 기록을 다시 확인하고 같은 문서의 구현 이해 섹션에 정리해줘. AI 없이도 내가 직접 구현 방식과 선택 이유를 설명할 수 있어야 해.

다음 내용을 실제 작업에 맞게 자세히 설명해줘.

1. 해결하려는 문제와 사용자, 목표와 필수 조건, 전체 처리 흐름
2. 핵심 로직의 입력값, 처리 순서, 조건과 예외, 출력값과 작은 예시
3. 주요 선택의 이유, 고려한 대안과 절충점, 조건이 달라질 때 바뀔 수 있는 판단
4. 자료의 출처와 연결 방식, 정제·제외 기준, 결과를 해석할 때 주의할 점
5. 기대 결과와 실제 결과의 대조 방법, 경계값과 실패 사례, 검증하지 못한 부분
6. 서비스가 있다면 화면 입력부터 API와 로직을 거쳐 결과가 표시되기까지의 흐름, 필요한 권한과 오류 처리
7. 작업 기록에서 확인되는 AI의 제안이나 구현, 사람이 확인하거나 수정한 내용과 근거
8. 현재 결과로 주장할 수 있는 것과 없는 것, 남은 기술 부채와 개선 우선순위

준비 단계에서 이해 자료로 활용할 수 있게 작성해줘. 실제 평가에서의 AI 사용은 안내된 규칙을 따를 거야. 각 항목에서 중요한 용어는 쉬운 말로 풀어주고, 해당 설명을 확인할 수 있는 파일과 위치를 함께 적어줘. 실제로 사용하지 않은 기술이나 수행하지 않은 검증은 예시로 소개하더라도 실제 작업과 명확히 구분해줘. 내가 단순 암기하지 않도록 왜 그런지와 조건이 바뀌면 무엇이 달라지는지도 설명해줘.

### 11-3. 핵심 내용 설명 연습

실제 요구사항, 구현, 검증 결과와 11-2의 이해 자료를 바탕으로 내가 이해한 내용을 직접 설명할 수 있게 같은 문서의 설명 검토 섹션에 주제를 정리해줘.

문제 정의와 요구사항, 데이터와 처리 흐름, 접근 방식을 선택한 이유, 예외와 검증, 결과 해석과 한계, AI 활용과 검토 과정 중 실제 작업에 해당하는 주제를 고르게 다뤄줘. 단순히 용어의 뜻만 확인하지 말고 여러 조건을 함께 고려해 선택 이유와 근거, 절충점이나 반례까지 설명할 수 있도록 해줘.

각 주제에는 이해를 확인할 질문, 답변에 포함할 핵심 내용, 실제 파일이나 검증 근거, 조건이 바뀌었을 때 생각해볼 사항을 정리해줘. 실제 구현을 바탕으로 간결하면서도 이유와 근거가 빠지지 않은 설명 예시도 작성해줘. 근거가 부족한 내용은 미확인으로 표시하고 구현하지 않은 기능을 전제로 삼지 마. 질문마다 같은 설명을 반복하지 않도록 서로 다른 판단과 근거를 다뤄줘.

잘 설명한 부분과 수정이 필요한 부분을 실제 근거와 함께 짚어주고, 내 표현을 최대한 살린 수정 예시를 보여줘. 추가로 확인할 파일과 공부할 내용을 정리해줘.

# 필요할 때 세션을 나눠서 진행하기

5번까지는 한 세션에서 진행하고, 이후 독립 작업이 가능할 때 핵심 로직과 웹을 나눌 수 있어. 웹이 필요 없거나 작업이 작으면 한 세션으로 진행해. 세션들은 대화를 자동 공유하지 않으므로 내가 필요한 파일 경로와 변경 사항을 각각 전달할게. 별도 작업 공간이라면 파일 공유와 통합 방법을 먼저 확인해.

## 세션을 나누기 전: 공통 계약과 소유권

```text
`docs/01-problem-map.md`부터 `docs/05-solution-plan.md`까지 필요한 문서와 원본을 확인해. `docs/05-solution-plan.md`에 각 세션의 담당 코드·문서 경로, 공유 파일과 공통 계약의 수정 책임자, 입출력 필드·타입·오류, 미확인 사항과 통합 순서를 정리해줘. 각 담당 문서는 한 세션만 수정하고 소유권을 넘길 때 이전 작업이 끝났는지 확인해줘. 실제 규칙과 임시 가정을 구분하고, 계약이 바뀌면 내가 다른 세션에 전달할 내용을 알려줘.
```

공통 계약은 `docs/05-solution-plan.md`가 기준이야. 웹 세부 계약은 `docs/web/02-api-contract.md`에 두고 기준과 연결해. 계약 변경은 공통 계약 책임자만 반영하고 내가 양쪽에 전달할게. 각 세션은 필요한 문서만 읽고 자기 담당 단계 문서에 변경 위치, 실제 검증과 남은 문제를 짧게 남겨줘. 별도 보고서나 상시 추적 세션은 만들지 않아.

## 세션 A: 기준안과 핵심 로직

```text
과제 README와 `docs/01-problem-map.md`부터 `docs/05-solution-plan.md` 중 필요한 문서와 원본을 읽어줘. 필요한 경우 6번 기준안을 확인하고, 7번 작은 예제와 기대 결과를 만든 뒤 8번 핵심 로직을 구현해줘. 각 단계의 지정 문서에 실행 명령, 실제 결과와 미검증을 남겨줘. 공통 계약을 변경해야 하면 이유와 영향을 알려줘. 웹 세션이 맡은 파일은 수정하지 마.
```

## 세션 B: 웹사이트

웹 1~5 프롬프트를 사용해. 과제 README, `docs/01-problem-map.md`, `docs/05-solution-plan.md`와 필요한 자료·규칙 문서를 전달하고 담당 파일을 알려줘. 핵심 로직이 아직 없다면 계약에 맞는 임시 결과임을 표시하고, 연결 후 실제 결과로 재검증해.

## 별도 세션: 기술 부채 관리

기술 부채 전용 세션을 시작할 때 첫 번째 프롬프트를 한 번 사용해. 이후 같은 세션에서 두 번째 프롬프트에 부채 번호나 파일 경로만 넣어 한 건씩 요청해. 다른 세션의 대화가 자동 공유된다고 가정하지 말고, 현재 작업 중인 세션과 수정하면 안 되는 파일을 내가 알려줄게.

### 1. 기술 부채 세션 시작

```text
이 세션은 내가 지정하는 기술 부채를 한 건씩 해결하는 전용 세션이야. 앞으로 다음 원칙에 따라 작업해줘.

먼저 시험·과제 지침, 과제 README, 기존 부채 관리 방식 또는 `docs/debt/README.md`를 읽고 실제 과제 작업 공간과 부채 기록 위치를 확인해줘. 과제에서 다른 부채 경로를 사용한다면 그 경로를 우선해줘. 현재 미해결 부채의 번호·제목·파일 경로를 간단히 확인하고, `solved/`는 해결 이력으로 구분해줘. 부채가 없거나 기록에 접근할 수 없으면 그 상태를 알려줘.

내가 부채 번호 또는 파일 경로를 지정하면 그 항목 하나만 처리해줘. 해당 부채 파일, 관련 단계 문서와 실제 코드·설정·검증 근거를 필요한 범위에서 읽고 문제의 현재 상태, 영향과 원인을 확인해줘. 오래된 기록이나 추측만으로 해결 여부를 판단하지 마. 번호가 모호하거나 파일이 없으면 임의로 선택하지 말고 알려줘. 부채가 여러 건 쌓여 있어도 내가 지정하지 않은 항목은 해결하지 마.

지정한 항목을 해결할 수 있다면 확인된 원인에 맞춰 필요한 범위만 수정하고, 관련 검증과 영향받는 회귀 검사를 실행해줘. 실제 변경 위치, 실행한 명령·결과와 미검증 사항을 부채 기록에 남겨줘. 수정과 검증이 모두 끝난 경우에만 부채 지침에 따라 같은 번호와 이름으로 `solved/`로 옮겨줘. 재현하지 못했거나 검증하지 못한 항목은 미해결로 남기고 이유와 다음 조치를 적어줘. 테스트를 실행하지 않았다면 통과했다고 말하지 마.

내가 알려준 다른 세션의 담당 범위와 공유 파일의 수정 책임을 확인해줘. 다른 세션이 수정 중인 코드·문서나 공통 계약은 직접 수정하지 말고, 담당자에게 내가 전달할 문제와 요청을 알려줘. 작업 상태를 알 수 없어 충돌 가능성이 있는 파일도 수정하지 마. 부채 파일의 수정·이동은 지정된 담당자 한 명이 수행하고, 담당자가 따로 있으면 내가 전달할 갱신 내용을 알려줘. 세션 간 대화나 파일 공유를 자동으로 가정하지 마.

지정한 항목을 해결하는 데 다른 부채의 변경이 반드시 필요하거나 별도 문제가 발견되면 연관성과 영향을 알려주고, 다른 부채는 임의로 수정하거나 해결하지 마. 각 요청을 마칠 때 지정 항목의 해결·검증 상태, 변경 위치, 실제 검증 결과, 부채 파일의 현재 경로와 다른 세션에 전달할 내용을 간결히 알려줘. 별도의 세션별 진행 보고서는 만들지 마.

지금은 준비만 해줘. 과제 지침과 부채 관리 방식을 읽고 미해결 목록을 확인한 뒤, 코드를 수정하거나 부채를 해결하지 말고 내가 항목을 지정할 때까지 기다려줘.
```

### 2. 지정한 기술 부채 한 건 해결

```text
다음 기술 부채를 해결해줘: [부채 번호 또는 파일 경로]
```

## 통합과 검증

담당 작업이 끝나면 필요한 단계 문서와 실제 코드·계약을 대조해. `docs/10-independent-verification.md`에 통합 검증 명령, 실제 결과, 실패와 미검증을 기록해. 웹 화면은 내가 직접 확인하고 전달한 결과만 기록해. 중요한 미해결 문제는 기존 부채 기록이나 `docs/debt/README.md`에 따라 중복 없이 관리하고, 여러 세션이 동시에 부채 번호를 만들지 않도록 한 담당자를 정해. 필수 기능과 정확성을 막는 문제는 통합을 기다리지 않고 수정·검증해.
