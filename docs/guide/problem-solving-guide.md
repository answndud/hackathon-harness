# 문제 해결·알고리즘 설계·검증 가이드

이 문서는 정답이 정해지지 않은 업무 과제를 분석하고, 구현의 판단 근거를 남기기 위한 범용 지침이다. 재응시 문제·평가 기준을 예측하거나 특정 알고리즘을 정답으로 가정하지 않는다. 시험의 공지·과제 README·상위 지침을 우선한다. 후속 서술형에서 AI 사용이나 문서 열람이 가능한지는 공식 안내로 확인한다.

## 1. 업무 문제를 구현 가능한 문제로 바꾸기

- **목표와 사용자:** 누가 어떤 행동이나 결정을 하기 위해 무엇을 개선하는가? 관리자와 일반 사용자의 역할이 다르면 각각의 작업을 나눈다.
- **입력과 출력:** 제공 데이터, 한 행의 의미, 단위, 시점, ID와 기대 결과의 형식·이용자를 확인한다. 근거 없는 데이터·목표값·규칙을 만들어내지 않는다.
- **성공 기준:** 정확도·소요 시간·비용·처리량·공정성·편의성 중 과제에서 중요한 지표와 계산법을 확인한다. 서로 충돌하면 우선순위를 묻는다.
- **제약:** 반드시 지켜야 하는 조건과 개선을 원하는 선호 조건을 구분한다. 권한, 처리 기한, 자원 한도, 필수 데이터, 실행 환경을 확인한다.
- **근거와 미확인:** 자료의 파일·위치, 담당자 답변, 추정·가정을 구분해 기록한다. 결과를 바꾸는 모호한 조건만 묻고, 담당자에게는 응시자가 직접 전달한다.

질문 예: “한 건의 기준 단위는 무엇인가요?”, “반드시 지켜야 할 조건과 선호 조건은 무엇인가요?”, “기존 결과와 비교할 실제 데이터가 있나요?”, “조건을 모두 만족할 수 없으면 어떤 결과를 보여줘야 하나요?”

## 2. 문제 유형별로 접근하기

| 문제 유형 | 먼저 확인할 것 | 가능한 접근 |
|---|---|---|
| 집계·분석 | 한 행의 의미, 기간, 분자·분모, 중복·결측 | 단순 집계와 명세 기반 규칙, 경계값 확인 |
| 분류·판정 | 판정 기준과 결과의 영향, 오류 비용 | 명시된 규칙부터 구현하고 경계 사례 검증 |
| 배정·스케줄 | 자원·수요, 필수 제약과 우선순위 | 설명 가능한 기준선과 배정 절차, 제약 충족 확인 |
| 경로·순서 | 방문 대상·시간·용량, 거리 또는 시간의 출처 | 기존 경로 평가, 단순 휴리스틱, 필요 시 제약 최적화 |
| 예측·추천 | 실제 목표와 평가 기준, 데이터 시점과 누수 | 단순 기준선과 대안 비교. 학습 데이터가 없으면 한계 명시 |
| 업무 웹 시스템 | 역할별 업무 흐름, 입력·저장·조회, 접근 권한 | 필수 사용자 경로를 입력부터 결과까지 우선 연결 |

접근법은 선택지일 뿐 정답이 아니다. 문제 규모, 제공 자료, 환경과 남은 시간에 맞춰 고른다.

## 3. 알고리즘과 설계 결정

1. **기준선:** 제공된 기존 방식과 결과를 확인해 같은 조건에서 평가할 수 있는지 살핀다. 없다면 재현 가능한 단순 방식을 기준선으로 두되 기존 운영 실적과 혼동하지 않는다.
2. **실제 처리 순서:** 입력 검증 → 데이터 정리 → 계산 또는 배정 → 조건 확인 → 결과 출력의 흐름을 과제에 맞게 정의한다. 각 단계의 입력·출력과 예외를 설명할 수 있어야 한다.
3. **대안 선택:** 구현 가능성, 결과 품질, 계산 시간, 설명 가능성, 의존성과 운영 비용을 고려한다. 복잡한 모델이나 외부 서비스는 필요한 근거와 사용 가능성이 있을 때만 도입한다.
4. **제약과 실패:** 제약 위반 후보를 어떻게 처리하는지, 결과가 없거나 미처리 항목이 생겼을 때 어떻게 표시할지 정한다. 탐색 시간 초과와 불가능하다고 증명된 경우를 구분한다.
5. **기록:** 실제 선택, 이유, 검토한 대안, 포기한 범위, 가정과 단점을 기존 과제 문서에 간결하게 남긴다. 검토하지 않은 대안을 검토했다고 적지 않는다.

전역 최적성을 증명하지 않았다면 “최적”이라고 단정하지 않는다. 처리 순서나 가중치가 결과에 영향을 줄 수 있으므로 적용한 기준과 종료 조건을 설명한다.

## 4. 기존안과 개선안 비교

- 동일한 입력, 대상, 시간대, 산식, 제약과 실행 환경에서 평가한다. 기준이 다르거나 기존 데이터가 없으면 공정한 비교가 불가능하다고 밝힌다.
- 정확성과 필수 조건 충족을 먼저 확인한다. 일부 입력을 누락하거나 오류를 빨리 반환해 빨라진 결과를 개선으로 판단하지 않는다.
- 과제에 맞는 지표의 단위·분모·산식·결측 처리를 기록한다. 처리 시간과 품질 지표는 별도로 설명한다.
- 난수가 있으면 시드와 반복 횟수를 기록하고 변동을 확인한다. 한 번의 측정이나 제한된 데이터로 일반 성능을 단정하지 않는다.
- 결과가 좋아진 이유는 실제 코드·측정으로 뒷받침되는 범위까지만 설명한다. 측정하지 않았다면 예상 효과와 미검증을 구분한다.

## 5. 검증: AI 출력도 독립적으로 확인

| 대상 | 확인할 내용 |
|---|---|
| 핵심 계산 | 명세·수계산으로 만든 작은 입력과 독립 기대값 대조 |
| 경계·예외 | 빈 입력, 중복, 결측, 기준값과 동일한 값, 허용 범위를 벗어난 값 |
| 제약·배정 | 중복 배정·미배정, 자원 한도, 필수 조건 위반과 처리 결과 |
| API·데이터 | 실제 요청·응답, 유효성 검사, 저장 후 재조회와 오류 처리 |
| 권한·화면 | 서버에서 역할과 본인 접근을 제한하는지 확인하고 화면 흐름은 응시자가 직접 확인 |
| 비교·성능 | 같은 조건의 기준선과 결과 일치 여부, 실제 측정 및 미측정 항목 |

검증마다 실제 입력·기대값의 근거·실행 명령 또는 수동 절차·실제 결과·관련 파일 위치를 남긴다. 테스트를 작성하기만 했다면 실행했다고 말하지 않는다. AI의 제안을 확인한 뒤 그대로 적용했어도 무엇을 어떻게 대조했는지 설명할 수 있다.

## 6. 구현부터 사용자 화면까지

과제의 구조에 맞춰 **사용자 입력 → API 또는 처리 진입점 → 검증 → 핵심 로직 → 저장·조회 → 응답·화면**의 흐름을 추적한다. 각 단계의 실제 파일·함수와 데이터 형식을 확인한다. 저장이 없다면 없다고 설명하고, 모의 데이터나 임시 저장이라면 그 사실을 밝힌다. 인증이 필요한 경우 관리자와 일반 사용자 또는 개인 데이터의 접근 범위를 서버 측에서 확인하며, 과제에 필요하지 않은 시스템을 추가하지 않는다.

## 7. 구현 중 남길 설명 근거

기존 요구사항·계획 문서를 우선 재사용하고, 허용되는 과제 작업 공간에 짧게 기록한다. 별도의 대형 보고서를 강제하지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 문제와 근거 | 목표·필수 규칙·출처·가정·미확인 사항 |
| 알고리즘 | 실제 입력·처리 순서·출력, 목적·제약, 실패·예외 처리 |
| 선택과 대안 | 실제 검토한 선택지, 선택·제외 이유와 단점 |
| AI 검증 | 확인이 필요했던 제안, 검증 방법과 실제 결과, 후속 조치 |
| 기존 대비 | 기준선과 입력·조건·산식·측정 결과·한계 |
| 증거 위치 | 구현 파일·함수, 테스트·비교 파일, 실행 명령 또는 수동 절차 |
| 미해결 | 실패·미검증·데이터 부족 및 영향 |

구현 단계에서 AI 사용이 허용된다면 Codex 요청 예시:

> 실제 자료와 코드를 기준으로 문제 목표, 입력·처리·출력, 주요 규칙·제약과 근거를 정리해라. 실제 선택과 대안·단점, 실행한 검증과 결과, 관련 파일 위치 및 미확인 사항을 기존 과제 문서에 간결하게 기록해라. 하지 않은 비교나 테스트는 만들지 마라.

> 기존안과 변경안을 같은 입력·조건·산식으로 평가할 수 있는지 확인해라. 가능하면 정확성과 과제 지표를 비교하고 재현 방법을 기록해라. 불가능하면 부족한 자료와 미검증 사유를 명시해라.

## 8. 짧은 가상 예시: 배차 노선

단일 차량이 D에서 출발해 정류장 A·B를 방문한 뒤 C에 도착한다고 가정한다. 이동시간이 D→A 4분, A→B 3분, B→C 5분이면 첫 순서는 **12분**이다. D→B 7분, B→A 3분, A→C 8분이면 반대 순서는 **18분**이다. 다른 조건이 같고 이 두 순서만 비교했다면 첫 순서가 6분 짧지만, 이것만으로 다차량 배차 전체의 최적성을 주장할 수는 없다.

실제 배차 문제라면 정원·도착 시각·직원 배정·미배정과 데이터 출처를 별도로 확인해야 한다. 직선거리를 대용치로 썼다면 도로·교통이 반영되지 않은 한계도 설명한다. 정류장 순서만 개선하고 배차 수나 탑승 인원 제약을 검증하지 않았다면 배차 전체가 개선됐다고 주장하지 않는다.

## 9. 서술형 답변 구성

**문제·목표 → 실제 접근법 → 선택 이유와 대안 → 독립 검증과 실제 결과 → 확인할 파일 위치 → 한계** 순서로 답한다. 질문이 “개선됐다”거나 “최적이다”라고 전제해도 입증하지 못한 내용은 먼저 바로잡는다. 후속 문항에서 AI가 금지되어 있다면 AI를 사용하지 않으며, 문서 열람도 허용 여부를 확인한다.
