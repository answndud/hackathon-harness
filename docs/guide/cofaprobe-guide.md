## 평가 환경과 과제

- **실무형 문제:** 완전한 명세와 정답이 주어지기보다, 불완전한 요구사항에서 필요한 정보를 찾아 문제와 해결 범위를 구체화한다.
- **현업 담당자:** 일부 과제에서는 현업을 모사한 AI 페르소나에게 질문해 업무 맥락과 제약을 확인한다. 필요한 정보는 제공하지만 완성된 작업 순서를 대신 결정하지는 않는다.
- **도구 활용:** 파일·터미널·에디터·브라우저와 AI 코딩 도구를 이용하는 환경을 제공하며, 일부 환경에서는 개인 스킬도 가져올 수 있다. **이번 시험의 허용 범위는 별도 공지와 과제 안내가 우선한다.**
- **예시 과제:** 선수의 인터뷰 연습과 답변 검토 기능을 만들 때, 연습 방식과 지도자의 피드백 시점을 질문해 기능을 구체화하는 방식이 소개됐다.

## 평가하는 세 가지 관점

- **기술:** 필수 요구사항을 충족하는지, 기능이 작동하는지, 구조와 구현 품질이 적절한지 확인한다.
- **의도:** 문제와 목표를 이해하고, 질문·설계·위임·검증을 통해 AI 작업의 방향을 주도하는지 살핀다.
- **인지:** AI가 만든 결과를 이해하고 중요한 선택의 이유와 제품 요구사항과의 관계를 설명할 수 있는지 확인한다.
- 세 관점은 구현을 서두르며 남길 수 있는 **기술 부채**, 목적과 실제 작업의 차이에서 생기는 **의도 부채**, 결과물을 충분히 이해하지 못해 생기는 **인지 부채**와 연결된다.

## 과정·비용·검증

- 인터뷰에 따르면 여러 평가 에이전트가 코드·화면·실행 상태·작업 기록을 나눠 분석하고, 판단 근거를 실제 결과에 연결한다.
- AI 도구 사용과 토큰·비용도 살핀다. 호출을 줄이는 것만으로 우수한 결과가 되는 것은 아니며, 불필요한 반복과 충분한 검증 사이의 균형이 필요하다. **이번 시험의 구체적인 배점·산식은 확인되지 않았다.**
- 개발진은 모델별 평가 결과가 알려진 성능 경향과 일치하는지 시험한 사례를 소개했다. 이 사례만으로 모든 참가자에 대한 평가 정확성이 보장되는 것은 아니다.

## 제품에 필요한 선택을 하는 능력

- AI가 정교한 코드를 작성하더라도 현재 사용자와 업무에 필요하지 않은 기능이나 복잡한 구조를 추가할 수 있다. 실제 사용 조건에서 필요한 수준인지 판단해야 한다.
- 인터뷰에서는 읽기 중심 API에 불필요하게 엄격한 제어를 더해 복잡성이 커진 사례를 들었다. 일반적으로 좋은 설계라는 이유만으로 모든 상황에 적합한 것은 아니다.
- 개인 도구·스킬 활용은 실제 업무 역량의 일부로 볼 수 있지만, 참가자별 준비 수준의 차이에 따른 공정성 문제도 논의됐다.

## 도메인 경험이 결과물에 기여한 사례

- 뷰티 매장에서 약 2년 일했고 전문 개발 경력은 없던 참가자가 화장품 쇼핑몰 과제에서 상위권 평가를 받았다.
- 고객과 상품에 대한 경험을 바탕으로 필요한 기능을 판단하고 AI를 활용해 구현한 것이 강점으로 소개됐다. 한 사례가 모든 비개발자의 직무 대체 가능성을 입증하는 것은 아니다.

## 시험 중 다시 집중하기 위한 실전 메모

아래는 위 인터뷰의 설명과는 별도로, 제한된 시간에 활용하기 위한 **운영 제안**이다. 공식 채점표나 출제 예측이 아니다. 시험 중에는 최신 공지와 과제 README를 먼저 따른다.

### 머리가 멍해졌을 때: 네 가지만 확인

1. **목표:** 누가 무엇을 결정하거나 처리할 수 있어야 하는가?
2. **현재:** 지금 실제로 작동하는 것은 무엇인가? 실행 결과로 확인했는가?
3. **막힌 지점:** 필수 기능을 막는 문제가 무엇인가? 파일·입력·오류 한 가지로 좁힐 수 있는가?
4. **다음 행동:** 남은 시간에 정답이나 작동 여부를 바꿀 가장 작은 작업은 무엇인가?

정리가 안 되면 Codex에게 “현재 필수 요구사항, 실제 완료·실패·미검증, 다음 작업 1개만 근거와 함께 정리해라”라고 요청한다. 보고만 믿지 말고 실제 파일과 실행 상태를 확인한다.

### 상황별로 한 번에 하나씩

| 상황 | 지금 할 행동 |
|---|---|
| 요구사항이 모호하다 | 자료에서 먼저 답을 찾고, 구현이 달라지는 질문 1~3개를 정리해 현업 담당자에게 직접 묻는다. 답이 없으면 가정과 영향을 표시한다. |
| 시작했는데 진도가 안 난다 | 한 사용자의 필수 작업 하나를 정하고 입력→처리→출력까지 연결한다. 차트·스타일·추가 구조는 그다음에 판단한다. |
| AI 결과가 그럴듯하지만 불안하다 | 정답을 바꾸는 값·조건·예외를 원자료와 대조한다. 중요한 계산은 작은 입력과 독립 기대값으로 검증한다. |
| 같은 오류를 반복 수정한다 | 동일 입력으로 재현하고 로그에서 실패 위치를 좁힌다. 추측성 수정을 멈추고 가설 하나만 시험한다. |
| 기능을 더 넣고 싶다 | 필수 요구인지 확인한다. 선택 기능이라면 남은 검증·수정·제출 시간과 비교해 보류할 수 있다. |
| 에이전트가 오래 멈춘 것 같다 | 승인 대기·실행 중·완료를 먼저 구분한다. 플랫폼 오류라면 안내에 따라 신고하며 타이머가 멈춘다고 가정하지 않는다. |
| 시간이 부족하다 | 필수 기능의 중대한 결함, 마지막 검증, 파일 저장과 제출을 우선한다. 미완료 항목을 숨기지 않는다. |

### 짧은 요청 예시

**업무를 확인할 때**

> 제공 자료에서 확인된 규칙과 미확인 사항을 구분해라. 구현을 바꾸는 질문 3개와 각각의 영향만 제시해라. 담당자에게는 내가 직접 묻는다.

**작업을 맡길 때**

> [필수 기능]의 입력→처리→출력 경로부터 구현해라. 기존 환경을 유지하고 정상 사례와 중요한 경계 사례를 검증해라. 결과와 남은 한계를 짧게 보고해라.

**오류를 수정할 때**

> [입력]으로 [오류]를 재현하고 로그로 실패 위치를 확인해라. 근거가 있는 가설 하나를 검증해 최소 수정한 뒤 기존 실패와 정상 사례를 다시 실행해라.

**제출을 준비할 때**

> 필수 요구사항별 구현 위치와 마지막 관련 변경 이후의 실제 검증 결과를 대조해라. 미커밋·신규 파일을 포함하고 완료·실패·미검증을 구분해라.

요청은 현재 상황에 맞게 바꾼다. 스킬이 필요하면 이름을 명시하고, 자동 검색이 안 되면 저장소의 해당 `SKILL.md`를 직접 읽어 적용하도록 요청한다.

### 모델과 토큰: 절약보다 재작업까지 포함한 효율

복잡한 요구사항·핵심 설계·어려운 오류는 품질을 우선하고, 범위가 분명한 단순 작업은 경제적인 모델을 고려한다. 현재 환경에서 모델 변경과 추론 수준 조절이 가능한지 확인한 뒤 응시자가 선택한다. 시험 플랫폼의 비용 산정 방식은 확정되지 않았으므로 공개 API 단가를 시험 점수로 단정하지 않는다. 반복 호출·큰 출력은 줄이되 핵심 검증은 생략하지 않는다.

### 제출 전과 후속 서술형

- **본 과제:** 필수 파일의 경로·내용·저장 상태와 실제 실행 결과를 확인한다. 미리보기에서도 타이머가 진행되므로 여유를 둔다. 본 과제 확정 후에는 수정할 수 없다는 안내를 확인한다.
- **서술형:** 본인이 한 결정, 이유, 구현, 실제 검증과 한계를 질문에 맞게 직접 설명한다. 질문의 전제가 구현과 다르면 차이를 먼저 밝힌다. 안내된 대로 AI와 복사·붙여넣기 제한을 따른다.
- **시간:** 본 과제 최대 180분과 후속 문항 시간이 각각 보장되는 것은 아니다. 문항 생성 대기에도 전체 종료 시각이 적용되므로 화면의 남은 시간과 최신 안내를 확인한다.
