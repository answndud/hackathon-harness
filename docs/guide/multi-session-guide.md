# Codex 다중 세션 작업 가이드

이 가이드는 주제가 정해지지 않은 제한 시간 과제를 여러 Codex 세션으로 해결할 때 사용하는 참고 자료다. 시험 공지·플랫폼 제한·과제 지침이 우선한다. 실제로 여러 터미널이나 세션이 허용되는지 먼저 확인하고, 지원되지 않거나 금지되면 한 세션에서 같은 역할을 순차 수행한다. 과제마다 필요한 역할만 선택한다.

문제 정의·알고리즘·비교·증거 기록의 자세한 기준은 [문제 해결 가이드](problem-solving-guide.md)를 따른다. 이 문서는 역할 분담, 계약, 전달과 통합에 집중한다. 업무 담당자와의 대화, 브라우저 조작 및 최종 제출은 응시자가 직접 수행한다.

## 시작할 때

1. 총괄 세션에서 과제 README, 제공 자료, 기존 지침과 실행 환경을 확인한다. 필수 기능·제약·완료 기준과 변경 가능 범위를 짧게 정리한다.
2. 작업의 성격과 의존관계에 따라 세션을 나눈다. 각 세션은 별도의 맥락에서 독립적인 역할을 수행하며, 동시에 진행할지 순차 진행할지는 과제와 환경에 맞춰 정한다. 단순한 과제나 계약이 계속 바뀌는 초기에는 세션을 줄인다.
3. 총괄은 공통 데이터·API 계약, 담당 범위, 파일 소유권, 보고 방식과 통합 시점을 정한다. 계약이 미정인 부분은 가정으로 표시하고 변경 시 영향을 전달한다.
4. 각 터미널에 같은 과제 작업 공간 경로와 담당 지시를 직접 전달한다. 수동으로 연 별도 세션은 서로의 대화를 자동으로 읽거나 직접 보고한다고 가정하지 않는다.
5. 첫 정상 흐름을 조기에 연결한다. 필수 정확성·보안 검증과 제출 준비 시간을 남긴다.

### 총괄 세션 시작 프롬프트

> `docs/guide/multi-session-guide.md`와 `docs/guide/problem-solving-guide.md`를 읽고 과제와 기존 환경을 확인해라. 독립적으로 진행할 수 있는 핵심 로직·백엔드·프론트엔드·검증 업무를 필요한 만큼만 분리해라. 각 세션의 범위, 파일 소유권, 공통 데이터/API 계약, 의존성, 통합 순서와 검증을 간결하게 정리해라. 내가 다른 세션에 전달할 지시문도 만들어라. 개발 중 실제 선택과 검증 결과를 기록하고, 합의되지 않은 업무 규칙은 가정으로 표시해라.

여러 세션을 여는 것은 응시자의 선택이다. 지원이 확인된 도구로 위임하는 경우에도 소유권·계약·검증 원칙은 같다. 별도 터미널을 열거나 세션 간 메시지를 전달할 수 있는 기능이 자동으로 존재한다고 가정하지 않는다.

## 역할과 작업 경계

| 역할 | 책임 | 완료 및 전달할 내용 |
|---|---|---|
| 총괄·통합 | 목표·제약·범위 확인, 계약과 소유권 정리, 작업 분배·통합·최종 확인 | 확정 규칙과 미확인, 현재 계약, 통합 결과·남은 위험 |
| 핵심 로직·데이터 | 입력 데이터 확인, 규칙·계산·판정·분석·최적화 등 과제의 핵심 처리 | 실제 입력·출력과 제약, 구현 위치, 기준안·검증 결과와 한계 |
| 백엔드 | 필요한 API·서버 검증·인증·인가·저장·조회, 핵심 로직 연결 | 엔드포인트·요청·응답, 저장 및 권한 방식, 실행·검증 결과 |
| 프론트엔드 | 필요한 사용자 흐름·화면·상태·API 연결 | 화면·구현 위치, 실제 또는 임시 데이터 여부, 수동 확인 절차 |
| 독립 검증 | 명세에 근거한 기대값, 주요 제약·통합 흐름 확인 | 검증 입력·독립 기대값·실제 결과·재현 절차·미검증 사항 |

역할은 고정된 인원수가 아니다. 계산이 단순하면 총괄이나 백엔드가 핵심 로직을 맡고, 화면이 없으면 프론트엔드를 생략한다. 작업량이 작으면 백엔드와 프론트엔드를 한 세션으로 합친다. 검증은 구현과 독립된 관점으로 하되 별도 세션을 상시 유지할 필요는 없다. 시험의 실제 토큰·시간 제한이 있다면 이를 우선한다.

## 공통 계약과 충돌 방지

여러 세션에서 구현하기 전에 현재 과제에 필요한 부분만 정한다. 미정인 항목을 사실처럼 확정하지 않는다.

| 계약 | 확인할 내용 |
|---|---|
| 데이터 | 식별자·타입, 단위·시간대, 필수·선택값, 결측 처리, 원본과 결과의 위치 |
| 핵심 로직 | 호출 함수 또는 진입점, 입력·출력, 부작용·오류·처리 불가 결과 |
| API | 경로·메서드, 인증과 권한, 요청·응답 필드, 오류 상태, 페이징 등 필요한 조건 |
| 화면 | 사용자별 흐름, 로딩·빈 결과·오류, 서버 응답과 표시 형식 |
| 저장 | 저장 책임자와 위치, 생성·갱신·조회, 임시 데이터와 영속성 여부 |
| 검증 | 독립 기대값의 출처, 필수 제약, 정상·경계·실패 사례, 실행 환경 |

총괄은 계약과 변경사항을 기존 과제 문서에 짧게 기록한다. 기존 문서가 없고 규칙이 허용하면 과제 작업 공간의 `docs/requirements.md`를 이용한다. 과제 데이터는 하네스 원본에 남기지 않는다. 공통 문서는 한 세션이 편집하고 다른 세션의 보고를 반영한다. 민감 정보·비밀 값은 기록하지 않는다.

같은 작업 디렉터리의 별도 터미널은 보통 파일을 공유하므로, 각 세션에 실제 경로 단위의 수정 범위를 지정한다. 공통 타입·설정·의존성·DB 스키마·라우팅 같은 공유 파일은 소유자 한 명이 수정한다. 다른 세션은 필요한 변경을 총괄에 전달한다. 기존 변경사항과 신규 파일을 확인하고 다른 세션의 작업을 덮어쓰거나 되돌리지 않는다.

DB, 데이터 파일, 서버 포트, 패키지 설치, 생성 파일, 환경 변수도 공유·충돌할 수 있다. 실행 전에 대상과 소유자를 정하고 파괴적 초기화·동시 마이그레이션을 피한다. 변경을 합치기 전에는 다른 세션의 작업이 끝났는지 확인한다.

### 별도 디렉터리 사용 시

Git worktree 등의 사용은 규정·권한·시간과 통합 비용을 확인한 뒤 결정한다. 작업 디렉터리가 분리되면 다른 세션의 수정이 자동으로 반영되지 않는다. 데이터·의존성·설정의 접근 가능 여부와 제출 대상 경로도 확인해야 한다. 변경 내용을 통합할 때 기존 변경을 보존하고 충돌을 해결한 뒤 최종 제출 디렉터리에서 재검증한다. 자동 커밋·push·외부 배포는 하지 않는다.

## 진행 순서

1. **총괄 준비:** 문제·자료·환경을 확인하고 필수 사용자 흐름, 제약, 담당 범위와 계약을 정한다.
2. **독립 구현:** 핵심 로직과 백엔드·프론트엔드를 의존성에 맞게 시작한다. 화면은 계약에 맞춘 임시 데이터로 먼저 구현할 수 있으나 임시임을 표시한다. 백엔드와 핵심 로직의 연결 책임자는 한 명으로 정한다.
3. **조기 연결:** 핵심 입력 한 건이 처리·저장·조회·표시되는 최소 흐름을 연결한다. 실제 과제에 저장이나 화면이 없으면 해당 단계를 생략한다.
4. **검증:** 독립적인 작은 사례로 핵심 규칙과 필수 제약을 확인하고, 필요하면 기준안과 개선안을 같은 조건으로 비교한다. 불가능하거나 실행하지 못한 항목은 미검증으로 둔다.
5. **통합·마감:** 계약 변경과 미완료 작업을 확인하고 실제 데이터를 연결한다. 최종 변경 이후 영향을 받은 검사와 사용자 흐름을 다시 확인하고 제출·설명 시간을 확보한다.

## 세션별 요청 예시

대괄호는 실제 과제와 합의한 경로로 바꾼다. 각 세션에 과제 작업 경로, 현재 계약과 읽어야 할 문서도 함께 전달한다.

### 핵심 로직·데이터

> [담당 경로]에서 [핵심 처리]를 구현해라. 과제 자료의 입력·출력, 필수 규칙·제약을 먼저 확인하고 [공통 계약]을 따라라. 필요하면 기준안을 변경 전에 보존하고 같은 조건의 개선안을 평가해라. 독립 기대값으로 핵심 규칙과 예외를 확인하고 구현 위치·명령·실제 결과·선택 이유·한계를 보고해라. 담당 외 공유 파일 변경이 필요하면 제안만 해라.

### 백엔드

> [담당 경로]에서 과제에 필요한 API·서버 검증·저장·조회와 핵심 로직 연결을 구현해라. [공통 계약]의 입력·출력과 오류 처리를 따르고 필요한 경우 인증·인가를 서버에서 확인해라. 실제 요청·응답과 저장 후 조회를 검증하고, 실행 방법·파일 위치·결과·미검증 사항을 보고해라. 화면이나 공통 파일을 임의로 수정하지 마라.

### 프론트엔드

> [담당 경로]에서 [사용자 흐름]을 구현해라. [API 계약]을 따르고 정상·로딩·빈 결과·오류 중 필요한 상태를 표시해라. 임시 데이터를 쓰면 그 위치와 실제 API 연결 여부를 분명히 알려줘. 구현 경로와 내가 직접 수행할 화면 검증 절차·예상 결과·미확인 사항을 보고해라. 브라우저 자동 조작은 수행하지 마라.

### 독립 검증

> 과제 명세와 [검증 대상]을 대조해라. 구현 결과를 그대로 기대값으로 삼지 말고 명세나 수계산으로 작은 정상·경계·실패 사례를 정해 실제 결과와 비교해라. 필수 제약과 통합 경계, 필요한 경우 기준안 비교의 조건도 확인해라. 실패는 입력·명령·관찰 결과·파일 위치를 보고하고 미실행 검사를 통과로 쓰지 마라. 담당 외 코드는 수정하지 마라.

## 보고와 통합

작업이 끝나거나 계약이 바뀌면 각 세션에 다음 형식으로 짧게 보고하도록 한다. 수동 세션이면 응시자가 보고를 총괄에 전달한다.

```text
완료한 범위:
변경 파일·함수:
입력·출력 또는 계약 변경:
실행한 검증·실제 결과:
실패·미검증·한계:
다른 세션에 필요한 조치:
```

총괄은 보고만 믿지 않고 실제 파일과 호출 관계를 확인한다. 계약 변경 시 영향을 받는 세션에 응시자가 전달하고, 각자 반영했는지 확인한다. 기술 부채는 기존 과제 기록 또는 [부채 기록 지침](../debt/README.md)을 따르고 공통 문서에는 필요한 위치만 연결한다.

### 통합 시 요청 예시

> 각 세션의 보고와 실제 변경 파일을 대조해라. 공통 계약·데이터 형식·호출 관계의 불일치와 임시 데이터가 남은 곳을 확인하고 필요한 변경을 통합해라. 사용자 입력부터 핵심 처리, 필요한 저장·조회, 응답·화면까지 실제 흐름을 검증해라. 최종 변경 뒤 영향을 받은 검사를 다시 실행하고, 확인된 결과와 실패·미검증, 직접 확인해야 할 화면 절차를 구분해 보고해라.

화면은 응시자가 직접 조작해 확인하며, 코드·CLI·API 검사와 실제 화면 관찰을 구분한다. 제출 전에는 실제 제출 디렉터리·저장 상태·필수 파일과 실행 방법을 확인한다. 서술형 단계에서 AI와 문서 사용이 허용되는지 시험 지침을 따르고, 구현 단계에서 선택·검증·한계를 직접 설명할 수 있도록 한다.

## 시간과 자원

- 같은 자료를 모든 세션이 반복 분석하지 않도록 총괄이 필요한 맥락·계약·담당 범위만 전달한다. 핵심 자료와 근거를 생략해 오해가 생기지 않도록 한다.
- 세션 수보다 독립 작업 여부와 조정 비용을 우선한다. 모델 변경이나 별도 에이전트는 환경에서 지원되고 허용될 때만 사용한다.
- 막힌 세션에 무한히 재시도시키지 말고 원인·현재 상태·필요한 결정을 보고받는다. 독립 작업은 계속하되 계약 변경은 조정한다.
- 기능을 계속 추가하기보다 통합·검증·설명과 제출에 시간을 남긴다. 실행하지 못한 검사는 명시한다.
